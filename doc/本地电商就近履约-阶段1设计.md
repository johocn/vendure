# 本地电商 · 就近履约（阶段1）设计说明

> 目标：商品带**城市维度**，下单时按**顾客定位**从最近仓库/门店分配库存，并做**服务范围门禁（超区提示）**。
> 依赖：项目内已有 `PickupLocation`（门店/自提点，含经纬度 + 省市区）、`MultiChannelStockLocationStrategy`、`inventory-plugin`、`delivery-plugin`。

## 一、核心修正（重要）

既有 `logistics-plugin` 的 `ChannelStockAllocationStrategy.allocateFromStockLocation`（含 `nearest` 分支）挂载在 `orderOptions.stockAllocationStrategy` 上，而该接口**只决定"何时分配"**（`shouldAllocateStock`），core 从未调用 `allocateFromStockLocation` —— 它目前是**死代码**，"就近/优先级/库存优先"并未真正生效。

真正决定"从哪个位置分配"的扩展点是 `catalogOptions.stockLocationStrategy`（`StockLocationStrategy.forAllocation`）。因此本方案**不沿用死代码**，而是子类化 `MultiChannelStockLocationStrategy` 覆写 `forAllocation`。

## 二、实现位置

全部落在 `packages/logistics-plugin`（已随 `LogisticsPlugin.init()` 在 dev-config 启用，改动最小）：

| 文件 | 作用 |
|---|---|
| `src/location-utils.ts` | haversine 距离计算（公里） |
| `src/nearest-stock-location-strategy.ts` | `NearestStockLocationStrategy extends MultiChannelStockLocationStrategy`，覆写 `forAllocation`：按订单经纬度就近排序 + 按服务城市过滤 |
| `src/catalog-custom-fields.ts` | Product / StockLocation / Order 三类自定义字段 |
| `src/plugin.ts` | 注册上述自定义字段（`mergeCustomFields` 去重）并覆写 `config.catalogOptions.stockLocationStrategy` |
| `migrations/20260817_local-commerce.sql` | 数据库变更脚本（幂等），见下 |

## 三、数据模型

- **Product**：`belongCity`（归属城市）、`serviceCities[]`（服务城市列表）→ 前端按当前选城过滤/超区提示
- **StockLocation**：`lat`/`lng`（门店/仓库经纬度）、`serviceCities[]`（服务城市）→ 就近算法 + 超区门禁输入
- **Order**：`lat`/`lng`（下单定位）、`city`（服务城市）、`deliveryType`（delivery/pickup）

> 线上 `synchronize:true`，重启后 TypeORM 自动建列；SQL 脚本为参考/手工部署备份，幂等，可重跑。

## 四、就近分配逻辑（`forAllocation`）

1. 读订单定位（`orderLine.order.customFields.{lat,lng}`）；无坐标 → 退化为父类默认顺序。
2. 若订单带 `city`：先过滤出 `serviceCities` 含该城市的仓库；全部超区时保留原列表（前端已拦截，不中断下单）。
3. 带坐标时按订单与仓库距离升序排列后交父类做库存核算分配（源保库存/渠道逻辑不变）。

## 五、需配合的改动（后续/前端）

- **前端 nshop**：登录定位→选城→把 `lat/lng/city/deliveryType` 写入订单 `setOrderCustomFields`；商品列表按 `belongCity`/`serviceCities` 过滤并做超区提示；就近门店列表复用 `pickupLocations(lat,lng)` 查询。
- 城市级库存隔离、调拨/盘点/采购单据、库存策略矩阵归入**阶段2（仓库能力完整化）**。

## 六、激活步骤

1. 本插件已在 `lib/` 本地构建（`npm run build`，已通过）。
2. 重新编译 dev-server 生产产物 `dist/`（它静态 require `@vendure/logistics-plugin`），然后按部署铁律推送、重启 Vendure。
3. 重启后核对：`product`/`stock_location`/`order` 表新增列（或手动执行 SQL）。

## 七、验证

- 建 2 个 StockLocation（不同经纬度、服务城市分设）→ 同一商品两库都有库存，订单写不同 `lat/lng/city` → 检查 `Allocation.stockLocationId` 命中最远距离对应仓；超区 `city` 不下发中间件。
- 单据核对（后台 Admin 查看订单/仓位分配）。
