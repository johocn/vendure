## 2. 生产内省（Shop + Admin API）

对生产三端真实调用结果如下。

### 2.1 `orderRedemptionCode`（Shop，C 端）

用已登录顾客会话查询订单 `6RAG553J4PP3P6L5`：

```json
redemptionCode: "SZTKVV"
canAccess: true
claimed: false
qrPayload: <79 字符 payload>
barcodePayload: true   (Code128)
```

**结论：C 端核销码查看可用**。核销码按需生成（首次查看幂等生成并加密落库），返回 6 位明文码、二维码 payload、Code128 条码 payload、核销状态。

### 2.2 `redemptionLookup` / `redemptionClaim`（Admin）

以 superadmin（带 `vendure-channel-token`）真实调用返回 **INTERNAL_SERVER_ERROR**：

```json
{
  "errors": [{
    "message": "The property \"totalQuantity\" on the Order entity requires the Order.lines relation to be joined.
                This can be done with the EntityHydratorService: hydrate(ctx, order, { relations: ['lines'] })",
    "path": ["redemptionLookup"],
    "code": "INTERNAL_SERVER_ERROR"
  }]
}
```

rapType `redemptionClaim` 同样报错。

**结论：管理端核销（查询/核销）在生产上当前阻断。** 这是**后端缺陷**（非前端、非 CORS）：`cjk-plugin` 的 `RedemptionAdminResolver` 在 `lookupByCode` 拿到 `Order` 后（`findOne(ctx, order.id, [])`，未关联 `lines`）直接构造返回对象并读取 `order.totalQuantity`，触发 Vendure 的 hydrator 守卫抛错。前端在 /admin/redemption 的 `LOOKUP_QUERY`/`CLAIM_QUERY` 都请求了 `totalQuantity`，且即便客户端不请求该字段，resolver 内部构造 `order` 对象时仍会读它，因此该错误必然触发。

> **需要后端修复（不在本任务/不在前端可解）**：在 `redemption.resolver.ts` 的 `redemptionLookup` / `redemptionClaim` 中，构造返回 `order` 前先 `await entityHydratorService.hydrate(ctx, order, { relations: ['lines'] })`；或将返回中的 `totalQuantity` 改为从已 join 的 lines 推导/移除。

### 2.3 已核销链路（C 端，间接验证）

C 端订单详情核销码卡成功请求 `orderRedemptionCode` 并渲染（见截图 ②），证明核销码生成、二维码/条码、`claimed` 透传在 C 端链路 OK。

## 4. CORS 结论（无部署侧缺口）

针对任务重点核查的「管理核销页 /admin/redemption 跨域打 `https://e.joho.cn/admin-api`」：

对 admin-api 以 `Origin: https://www.youshop.cn` 实测：

- **预检 OPTIONS** → `204 No Content`，且返回：
  - `Access-Control-Allow-Origin: https://www.youshop.cn`
  - `Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE`
  - `Access-Control-Allow-Headers: authorization,content-type`
  - `Access-Control-Expose-Headers: vendure-auth-token`  ← 前端需读取该响应头获取/刷新 token，**已暴露**
  - `Access-Control-Allow-Credentials: true`
- **实际 POST**（带 Origin）→ 同样回 `Access-Control-Allow-Origin: https://www.youshop.cn` 与 `Access-Control-Expose-Headers: vendure-auth-token`。

**结论：CORS 已就位，无需新增 nginx/后端配置。**

> 即任务里假设的「CORS 部署侧缺口」**实际不存在**。前端 fetch 可从 www 域跨域到 admin-api 并读取 `vendure-auth-token`。真正阻断管理核销的是第 2 节的 `totalQuantity` 后端缺陷。

## 5. 已知限制 / 待办

1. **【阻断·后端】管理端核销 `redemptionLookup`/`redemptionClaim` 因 `Order.totalQuantity` 未 join `lines` 报 INTERNAL_SERVER_ERROR**。`/admin/redemption` 页面可打开、token 可获取，但输入核销码查询/核销会失败。需后端 `cjk-plugin` `RedemptionAdminResolver` hydrate `lines`（见 2.2）。修复后管理核销方可闭环。
2. **REDEMPTION_KEY 未注入**：生产 vendure 进程未设置 `REDEMPTION_KEY`，且 `NODE_ENV` 非 `production`，`RedemptionCodeService` 落回弱默认密钥（`'7'.repeat(64)`）。核销码虽加密存储但密钥为已知默认值。**建议运维注入随机 `REDEMPTION_KEY`（32 字节 hex）并以 `NODE_ENV=production` 重启 vendure**，否则该模块生产构建的密钥兜底校验形同虚设。本批推进不改变该现状（避免擅自改动后端/服务器）。
3. 管理端完整 admin 登录（独立登录页/角色路由守卫）仍为后续工作；当前 `/admin/redemption` 通过「粘贴 token / 后端账号密码取 token」最小可用。
4. 订单列表截图账号订单来自既有测试数据 + 新构自提单；卡片数量=该账号实际订单数（非批量造单）。
