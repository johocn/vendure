对生产三端真实调用结果如下。

### 2.1 `orderRedemptionCode`（Shop，C 端）


**结论：C 端核销码查看可用**。核销码按需生成（首次查看幂等生成并加密落库），返回 6 位明文码、二维码 payload、Code128 条码 payload、核销状态。

### 2.2 `redemptionLookup` / `redemptionClaim`（Admin）→ 已修复

**✅ 修复与重新部署（commit `c2533a089`）**：此前以 superadmin（带 `vendure-channel-token`）真实调用会因 `Order.totalQuantity` 未 join `lines` 抛 **INTERNAL_SERVER_ERROR**（后端 `cjk-plugin` `RedemptionAdminResolver` 的 `lookupByCode` 用 `findOne(ctx, order.id, [])` 直接读取 `order.totalQuantity` 触发 Vendure hydrator 守卫）。已在 resolver 构造返回 `order` 前 hydrate `lines` 并重新部署，生产 `redemptionLookup` 已端到端打通：

- 订单 `PPH8639XF4RD4ZDU` 核销码 `EC3Y6T` → `redemptionLookup` 返回 `totalQuantity: 5`，不再 500。
- `redemptionClaim` `rapType` 同步修复。

> 修复前基线（历史报错，供留档）：`The property "totalQuantity" on the Order entity requires the Order.lines relation to be joined...`。前端 /admin/redemption 的 `LOOKUP_QUERY`/`CLAIM_QUERY` 均请求 `totalQuantity`，且 resolver 构造 `order` 时必读该字段，故旧版本该错误必然触发。

### 2.3 已核销链路（C 端，间接验证）

C 端订单详情核销码卡成功请求 `orderRedemptionCode` 并渲染（见截图 ②），证明核销码生成、二维码/条码、`claimed` 透传在 C 端链路 OK。

## 4. CORS 结论（无部署侧缺口）

针对任务重点核查的「管理核销页 /admin/redemption 跨域打 `https://e.joho.cn/admin-api`」：

对 admin-api 以 `Origin: https://www.youshop.cn` 实测：

- **预检 OPTIONS** → `204 No Content`，且返回：
  - `Access-Control-Allow-Origin: https://www.youshop.cn`
  - `Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE`
  - `Access-Control-Allow-Headers: authorization,content-type`
  - `Access-Control-Expose-Headers: vendure-auth-token`  ← 前端需读取该响应头获取/刷新 token，**已暴露**
  - `Access-Control-Allow-Credentials: true`
- **实际 POST**（带 Origin）→ 同样回 `Access-Control-Allow-Origin: https://www.youshop.cn` 与 `Access-Control-Expose-Headers: vendure-auth-token`。

**结论：CORS 已就位，无需新增 nginx/后端配置。**

> 即任务里假设的「CORS 部署侧缺口」**实际不存在**。前端 fetch 可从 www 域跨域到 admin-api 并读取 `vendure-auth-token`。此前阻断管理核销的 `totalQuantity` 后端缺陷已于 commit `c2533a089` 修复并重新部署（见 2.2）。
