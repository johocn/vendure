# 拆单支付聚合 — 线上端到端验证（方案A 余额合单 / 方案B 非余额全拆）

> 日期：2026-08-29
> 环境：生产 qing（39.97.54.5），Shop API `https://e.joho.cn/shop-api`
> 涉及服务：`cjk-plugin` 的 `checkoutSplitted` 统一结算入口 + `decideAggregation` 聚合拆合引擎

## 1. 背景与设计要点

订单分箱后，结算时按「用户所选支付方式」决定是否拆单（`decideAggregation` 纯函数）：

- **方案 A（选余额 `balance-wallet`，全局共享钱包）**：全部箱跨租户/跨配送档案**合并为 1 个订单**，一次余额扣款。分组的 groupKey = `balance`。
- **方案 B（选非余额方式）**：**一律按箱全拆**，每个配送档案各构成 1 个独立订单、各自独立支付。不做「同租户且各箱白名单都含该方式就合单」的合并。分组的 groupKey = `box-${tenantChannelId}-${boxKey}`。

前端契约：结账支付提交**无论余额/非余额一律调用 `checkoutSplitted($method,$metadata)`**（返回 `[Order!]!`），由后端按所选方式回落为 1 单或多单，前端无需区分走 `addPaymentToOrder`。
`GetOrderBoxes` 必须选中 `availablePaymentMethodCodes`，供 PaymentBlock 白名单并集过滤。

## 2. 关键坑：Bearer 认证（线上实测排障结论）

Shop API 此部署的会话 token **必须用 `Authorization: Bearer <token>` 头发送**，才能延续同一会话。

- `vendure-auth-token` 响应头携带的是「最新 token」，用它作为请求头发送 **不会被识别**（返回 `FORBIDDEN: You are not currently authorized`），导致每次请求都被当作新匿名会话，从而每个 `addItemToOrder` 生成独立活动订单（拆单前的加购会散落多单）。
- 正确做法：**请求发 `Authorization: Bearer <token>`，响应后从 `vendure-auth-token` 头抓最新 token 再更新本地变量**，实现会话持久。
- 附带：`activeOrder { lines { sku } }` 会 400（`OrderLine` 无 `sku` 字段），查询行须用 `lines { id quantity productVariant { sku } }`。

## 3. 测试脚本

| 脚本 | 验证目标 | 位置 |
|---|---|---|
| `_online_split_flow.mjs` | 方案 B：非余额 → 按箱全拆 2 单 | 仓库根 |
| `_online_balance_flow.mjs` | 方案 A：余额 → 合 1 单 | 仓库根 |

两者流程一致：临时注册客户 → `login`（Bearer 会话）→ 加入分属两配送档案的变体（var6=SPK-BT-01/档案11、var31=COOK-GIFT-01/档案12）→ `setOrderShippingAddress(CN)` → `orderBoxes` 拿到 2 箱 → `checkoutSplitted(method=…)` → 打印返回订单数/行数/状态并判定是否符合预期。

运行：`node _online_split_flow.mjs` / `node _online_balance_flow.mjs`（需在 `d:\zhao\vendure`）。

## 4. 实测结果

### 方案 A（选 `balance-wallet`）✅
- 加购后 `orderBoxes`：`box:11`(档案11, 行171) + `box:12`(档案12, 行172)，白名单均为 `[fixed-aggregate-collection, balance-wallet]`。
- `checkoutSplitted(method="balance-wallet")` → 返回 **1 个订单** `J6F4CGR8Z2P9YNMH`，¥197，state `PaymentSettled`，订单内含 **2 行**（SPK-BT-01 + COOK-GIFT-01）。
- **符合预期**：两箱跨配送档案并为一单，一次余额结算。

### 方案 B（选 `fixed-aggregate-collection`）✅
- 加购后 `orderBoxes`：`box:11`(档案11, 行166) + `box:12`(档案12, 行167)，白名单同上。
- `checkoutSplitted(method="fixed-aggregate-collection")` → 返回 **2 个订单**：
  - `119` / `W1X2EB8ED6WCRAQ6`（源订单）→ SPK-BT-01，¥129，state `PaymentAuthorized`
  - `120` / `CRCTA23LAPVGS5WF`（新订单）→ COOK-GIFT-01，¥68，state `PaymentAuthorized`
- **符合预期**：非余额方式下按箱全拆为每配送档案一单，各自独立支付。

### 结果对照

| 项 | 方案 A（余额） | 方案 B（非余额） |
|---|---|---|
| 支付方式 | `balance-wallet` | `fixed-aggregate-collection` |
| 箱数 → 订单数 | 2 箱 → **1 单** | 2 箱 → **2 单** |
| 订单状态 | `PaymentSettled` | `PaymentAuthorized` |
| 行归属 | 2 行合并在源订单 | 各行拆到各自独立订单 |

## 5. 结论与回归建议

- 两条分派路径均由 `decideAggregation` 按所选支付方法正确驱动，`checkoutSplitted` 统一入口在前端无需感知即可回落为 1 单或多单，**方案 A / B 均达成设计语义**。
- 若后续改动涉及 `order-box-aggregation.ts`、`order-split.service.ts`、`order-split-shop.resolver.ts`、`order-box.service.ts`，建议重跑本验证脚本作为回归基线（余额路径 + 非余额路径各一次）。
