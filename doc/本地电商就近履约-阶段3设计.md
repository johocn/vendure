# 本地电商 · 就近履约（阶段3）设计说明

> 目标：在阶段1/2「就近分配 + 超区门禁 + 供销存账本 + 售后回补」基础上，落地三块能力：**库存策略矩阵**（按渠道/配送方式/会员等级差异化分配）、**多仓拆单出库**（就近优先余量拆单 + 管理员手动调单 + 每包裹独立计费）、**同城配送抽象网关**（Provider 抽象 + 模拟配送商）。
> 依赖：阶段1/2 已具备 `NearestStockLocationStrategy`、`OrderStockLedger` 账本、`inventory-plugin`、`delivery-plugin`、`after-sales-plugin`、cjk `PickupLocation`、member-level-plugin。

## 一、现状与关键决策

### 1.1 现状盘点（阶段1/2 交付）

| 能力 | 位置 | 状态 |
|---|---|---|
| 就近分配 + 服务城市门禁 + 自提锚点 | `logistics-plugin/nearest-stock-location-strategy.ts` | 已上线 |
| 按渠道发货策略（priority/stock-first/nearest 雏形） | `logistics-plugin/channel-stock-allocation-strategy.ts` | 遗留（`allocateFromStockLocation` 无调用方） |
| 供销存账本 `OrderStockLedger`（order:out / afterSales:in） | `inventory-plugin` | 已上线 |
| 售后退货库存回补（回补主仓） | `after-sales-plugin` | 已上线 |
| 自有司机配送 | `delivery-plugin`（`deliveryStaffId/deliveryStatus`） | 已上线 |
| 会员等级（成长值 → LV1..LV5） | `member-level-plugin` | 已上线 |

### 1.2 关键决策（已确认）

1. **拆单触发**：就近优先 + 余量拆单，当前仓不足时自动从次近仓补足。
2. **手动调单**：就近自动拆单后，管理员可手动调整出货仓及数量。
3. **拆单运费**：每包裹独立计费（N 仓拆单即 N 笔运费，结账合计一笔 + 明细落 JSON）。
4. **同城配送深度**：抽象网关 + 模拟配送商（MockProvider），真实平台后续按 code 插拔。
5. **实现路径**：方案一（单复合策略 + 原生多仓分配 + 拆单履约工作流），并在拆单层预留 `OrderSplitPlan` 抽象接口，可平滑升级到方案二 `OrderPackage` 持久化实体。
6. **文档组织**：三合一设计文档。

## 三、配置模型（Channel 自定义字段）

| 字段 | 现状 | 阶段3扩展 |
|---|---|---|
| `shippingStrategy` | `nearest/priority/stock-first` | 新增 `member`（会员等级专属） |
| `stockLocationPriority` | JSON `[{locationId,priority}]` | 复用 |
| `memberStockStrategy`（新增） | — | JSON：会员等级→优先仓列表 |
| `packageShippingRule`（新增） | — | JSON：每包裹独立运费规则 |

```json
// memberStockStrategy 示例
[
  { "level": "LV3", "locationIds": ["1", "2"], "fallback": "nearest" },
  { "level": "LV4", "locationIds": ["5"],      "fallback": "stock-first" },
  { "level": "LV5", "locationIds": ["6"],      "fallback": "nearest" }
]
```

**矩阵判定优先级**：
1. 会员等级专属（命中 `memberStockStrategy` 且 `locationIds` 有货）＞
2. 渠道 `shippingStrategy`（nearest / priority / stock-first）＞
3. 默认兜底：就近优先。

会员等级由 `member-level-plugin` 的 `Customer.customFields` 成长值 → 等级（阈值在 channel 级字段）计算。

## 四、库存策略矩阵分发逻辑

### 4.1 `MatrixStockLocationStrategy`（logistics-plugin，单一全局策略）

继承 `NearestStockLocationStrategy`，保持 `MultiChannelStockLocationStrategy` 的库存核算/渠道隔离，覆写 `forAllocation` 为矩阵分发统一入口：

```
forAllocation(ctx, stockLocations, orderLine, quantity)
  1) 解析订单维度
     deliveryType = order.customFields.deliveryType（standard / pickup）
     memberLevel  = 订单 Customer 成长值 → LV1..LV5
  2) 公共前置过滤（服务范围门禁）
     · 有 city → 过滤 serviceCities 含 city 的仓
     · deliveryType=pickup → 以自提点坐标替代顾客定位（沿用现有）
  3) 矩阵判定（命中即执行，自上而下）
     a. 会员专属命中（memberStockStrategy 含该等级且有货） → MemberExclusive
     b. shippingStrategy=nearest     → Nearest
     c. shippingStrategy=priority    → Priority
     d. shippingStrategy=stock-first → StockFirst
     e. 未配置/未命中 → 默认 Nearest
  4) 分配器执行 → 返回 LocationWithQuantity[]（可含多仓 = 余量拆单）
  5) 记录拆分明细 → OrderLine.stockLocationsJson
```

### 4.2 四种分配器规则

| 分配器 | 排序/过滤逻辑 | 数据依赖 |
|---|---|---|
| **Nearest** 就近 | 按订单坐标（pickup 用自提点）距离升序 | `location-utils.distanceKm` |
| **Priority** 优先级 | 按 `stockLocationPriority` JSON 的 `priority` 升序 | Channel 字段 |
| **StockFirst** 库存优先 | 服务范围内按 `stockOnHand` 降序 | 各仓可售量 |
| **MemberExclusive** 会员专属 | 命中 `memberStockStrategy[level].locationIds` 优先，仓无货/不足则回退 `fallback` | 等级→仓映射 |

> 会员专属「优先」语义：目标仓有货则优先分配，数量不足时剩余量走 `fallback` 规则（余量拆单）。同一等级可配多个 `locationIds`，内部按顺序 + 库存满足度分配。

### 4.3 配送方式维度（pickup 交互点）

- `deliveryType=pickup` 时仍按矩阵判定规则，但所有分配器以**自提点坐标**为锚（Nearest 排序、Priority/StockFirst 的服务范围过滤不变）。
- 自提场景会员专属规则同样生效（如钻石会员固定门店自提仓）。

### 4.4 拆分明细落库（预留 `OrderPackage` 平滑过渡）

- OrderLine 新增自定义字段 `stockLocationsJson`：`[{ locationId, quantity }]`，记录一行分配到的多仓明细。
- 现状由 `MatrixStockLocationStrategy` 写入；未来升级 `OrderPackage` 实体时数据源即此字段，**接口签名不变，平滑切换**。
- 保留 `stockLocationId`（主仓）兼容阶段1/2 售后回补定位逻辑。

### 4.5 与 `StockAllocationStrategy` 的关系

- `shouldAllocateStock`（`toState !== 'Cancelled'`）保留不动。
- 废弃遗留 `ChannelStockAllocationStrategy.allocateFromStockLocation`，分发职责全部收敛到 `MatrixStockLocationStrategy`。

## 五、多仓拆单出库与每包计费

### 5.1 `OrderSplitPlan` 抽象接口（预留 `OrderPackage` 平滑过渡）

```ts
// logistics-plugin / order-split-plan.ts
interface OrderSplitPlan {
    orderId: ID;
    packages: SplitPackage[];          // 每仓一包
}

interface SplitPackage {
    packageId: string;                 // 包号，如 P1/P2
    stockLocationId: ID;               // 出货仓
    lines: Array<{ orderLineId: ID; quantity: number }>;  // 每行在此包的数量
    estimatedShippingFee: number;      // 本包预估运费
    deliveryMode: 'self' | 'city';     // 自有司机 / 同城配送
    deliveryOrderId?: ID;              // 同城配送单关联
}
```

两个服务：
- `AutoSplitPlanService`：读订单各行 `stockLocationsJson` 自动生成默认计划（就近余量拆单结果）。
- `ManualSplitAdjustService`：管理员后台调单（改仓/改量），校验后生成最终计划。

### 5.2 拆单履约工作流

```
发货准备
  └ AutoSplitPlanService 读 stockLocationsJson → 默认每仓一包
  └ 后台「拆单发货」界面：展示各包行明细
       管理员手动调单：修改 行→仓、数量
       校验：每行数量守恒（Σ(packages 中该行数量) === 行原数量）
            + 每仓可售充足（assertSufficientStock）
  └ 确认 → 最终 OrderSplitPlan
发货执行
  └ 按包逐个创建 Fulfillment（Vendure 原生支持每单多 Fulfillment，
    每个带独立 lines:[{orderLineId, quantity}]）
  └ Fulfillment.customFields 新增 shippingFee / packageId（记本包实际运费）
  └ Shipped → core 写 RELEASE + SALE、ledger 每仓各记一条 order:out
  └ 特殊：deliveryMode=city 的包不在此步建 Fulfillment，
    延迟到骑手取货（pickup）时才创建并 Shipped（见 6.3），
    其余 self 包按上述流程立即建。
```

### 5.3 每包裹独立计费（`SplitShippingCalculator`）

1. **结账时**：`SplitShippingCalculator` 读取当前拆单计划，逐包按运费规则算出各包运费，**合计为一笔 ShippingLine**（不引入多 ShippingLine 复杂度），明细写入 `Order.customFields.packageShippingJson`：`[{packageId, locationId, fee}]`。
   - `packageShippingRule` JSON 结构（channel 字段）：
     ```json
     [{ "locationId": "1", "baseFee": 6, "perKmFee": 1.5, "freeThreshold": 99 }]
     ```
     未配置到仓的包按全局默认（`baseFee=10, perKmFee=2`）兜底。
2. **发货时**：每包创建 Fulfillment 记 `shippingFee`（实际运费）。
3. **调单差异**：调单后包/仓变化导致运费变动，记 `Order.customFields.shippingAdjustment`（正=补收、负=退）。本期**仅记录**，实际退款走售后流程，不做自动补扣。

> 前端订单详情按 `packageShippingJson` 展示「运费明细：包1 就近仓 ¥6、包2 次近仓 ¥12」。

### 5.4 账本与售后衔接

- **拆单发货**：每仓各写一条 `OrderStockLedger(order:out)`，`locationId` 精确到仓。
- **售后回补**：本期仍回补**主仓** `stockLocationId`（阶段2 逻辑不变），多仓按包回补列入后续。
- `stockLocationsJson` 为未来「按仓售后回补」与 `OrderPackage` 升级提供数据底座。

## 六、同城配送抽象网关（新插件 `delivery-gateway-plugin`）

### 6.1 Provider 抽象接口

```ts
// delivery-gateway-plugin / delivery-provider.ts
interface DeliveryProvider {
    code: string;                              // 'mock' | 'dada' | 'shansong' | 'fengniao'
    name: string;
    quote(ctx, req: DeliveryQuoteRequest): Promise<DeliveryQuote>;
    createDelivery(ctx, req: DeliveryCreateRequest): Promise<DeliveryCreateResult>;
    cancelDelivery(ctx, deliveryOrderNo: string, reason?: string): Promise<DeliveryCancelResult>;
    parseWebhook(payload: unknown): DeliveryStatusEvent;   // 平台回调解析
}
```

请求/结果模型（对齐主流平台字段，便于后续适配）：
- `DeliveryQuoteRequest`：`pickup{name,lat,lng}`、`dropoff{name,lat,lng,phone}`、`items[]`、`weight`、`deliveryType(instant|scheduled)`
- `DeliveryQuote`：`fee`、`feeDetail`、`etaMinutes`、`available`
- `DeliveryCreateResult`：`deliveryOrderNo`、`thirdPartyNo`、`status(pending|accepted)`、`fee`
- `DeliveryStatusEvent`：`deliveryOrderNo`、`status(accepted|pickup|delivered|cancelled|exception)`、`courierName/Phone`、`deliveredAt`、`reason`

### 6.2 配送单实体 `DeliveryOrder`

| 列 | 说明 |
|---|---|
| code | `TDS+时间戳` |
| orderId / packageId | 关联拆单包（5.1） |
| fulfillmentId 可空 | 发货后关联 Fulfillment |
| providerCode / thirdPartyNo | 平台标识 |
| status | `pending→accepted→pickup→delivered` / `cancelled` / `exception` |
| pickup / dropoff | 名称、地址、lat/lng、电话（快照） |
| itemsJson / fee / etaMinutes | 明细与费用 |
| acceptedAt / pickupAt / deliveredAt / cancelledAt / reason | 时间戳与原因 |

### 6.3 状态机与回写

```
createDelivery（配送单 pending）
  → 平台接单 accepted
  → 骑手取货 pickup（此时才建 Fulfillment → Shipped，扣库写 ledger）
  → 送达 delivered → Fulfillment Delivered → 订单 Delivered
  → cancelled / exception（reason 记录，走异常处理）
```

- **回写通道**：Provider 支持 webhook 回调（`callbackUrl`）；Mock 提供后台「模拟接单/取货/送达/取消」按钮直接触发内部事件，不依赖外网，便于本地验证闭环。
- **与 delivery-plugin 的关系**：现有 `delivery-plugin` 是**自有司机配送**（人工指派司机）。同城配送是**第三方平台配送**，两者并存——`SplitPackage.deliveryMode` 按包选择；选 `city` 时创建 `DeliveryOrder` 并回写驱动订单状态。

### 6.4 与计费/账本衔接

- 配送费在 `DeliveryOrder.fee` 与 `Fulfillment.shippingFee` 双记，纳入每包计费（5.3 的 `packageShippingJson` 运费明细）。
- 同城配送不产生额外库存流水（发货扣库已由 Fulfillment SALE + `order:out` ledger 覆盖）。

## 八、验证

- **矩阵**：同渠道不同会员等级订单分别命中 MemberExclusive/Priority/Nearest，服务日志可查命中规则；pickup 订单锚定自提点。
- **拆单**：双仓建库存、跨仓订单默认自动拆两包；后台手动调单改仓/改量，数量守恒校验拦截非法输入。
- **计费**：结账 `packageShippingJson` 出现每包运费明细、订单总额正确；发货后 Fulfillment 记录实际 `shippingFee`；调单差异记 `shippingAdjustment`。
- **同城**：Mock 创建配送单 → 接单 → 取货 → 送达全链路，Fulfillment/Order 推进到 Delivered；取消/异常留痕。
- **回归**：阶段1/2 就近分配 + 售后退货回补闭环不回归（跑既有 e2e 脚本）。
