# 本地电商就近履约 · 阶段10设计：履约闭环（订单状态机由包裹生命周期驱动 + 交易完成终态）

> 承接：阶段6（OrderPackage 状态机与状态回写）边界项之「业务规则门槛」之前的关键闭环——把包裹/配送生命周期聚合回写**订单级状态机**，补齐「支付 → 发货 → 送达 → 交易完成」完整履约闭环。
> 目标：拆单包裹（OrderPackage）与同城配送（DeliveryOrder）的生命周期变化，自动驱动订单（Order）状态在 `PartiallyShipped → Shipped → PartiallyDelivered → Delivered → Completed` 间流转；新增 `Completed`（交易完成）终态，支持**手动确认收货**与**自动交易完成**（Delivered 后 N 天）。

## 1. 背景与要解决的问题

当前履约链路已有三层状态机，但**订单层没有消费包裹生命周期**：

| 层级 | 状态机 | 状态来源 |
|---|---|---|
| 包裹层 | `OrderPackage`：pending→shipped→delivered/cancelled | [order-package.service.ts](file:///d:/zhao/vendure/packages/logistics-plugin/src/order-package.service.ts#L40-L45) `transition` 单一收敛点；由发货挂钩点/配送事件/`markPackageDelivered` 驱动 |
| 配送层 | `DeliveryOrder`：pending→accepted→pickup→delivered/cancelled/exception | `applyStatusEvent`（mock 事件 / 达达 webhook） |
| 订单层 | Vendure core 订单状态机：`PaymentSettled`…`Delivered` | **无人驱动**（见下） |

**订单层未被驱动的三个根因**：

1. `OrderService.createFulfillment` 只把 fulfillment 推到 `Pending`（[order.service.ts#L1770](file:///d:/zhao/vendure/packages/core/src/service/services/order.service.ts#L1770-L1773)），而 core 的订单推进逻辑 [handleFulfillmentStateTransitByOrder](file:///d:/zhao/vendure/packages/core/src/config/fulfillment/default-fulfillment-process.ts#L128-L162) 仅在 fulfillment 转到 `Shipped`/`Delivered` 时触发 → **从未发生**，订单永远停在 `PaymentSettled`。
2. **city 包没有 fulfillment**（直达配送），core 的 fulfillment→order 联动对 city 包永不触发。
3. core 的 `checkFulfillmentStates` 守卫（[default-order-process.ts#L375-L400](file:///d:/zhao/vendure/packages/core/src/config/order/default-order-process.ts#L375-L400)）用 `orderItemsAreShipped/Delivered` 基于 fulfillment 校验 → **无 fulfillment 的 city 包推动订单转 Shipped/Delivered 会被直接拦截**。
4. 本 fork 订单状态机**没有 `Completed`（交易完成）终态**（[order-state.ts](file:///d:/zhao/vendure/packages/core/src/service/helpers/order-state-machine/order-state.ts#L42-L48) 仅有 Delivered）。

**要解决的问题**：让包裹生命周期（无论 self 还是 city）统一驱动订单状态机，直至 `Completed`，形成可运营、可对账的履约闭环；同时保证 core 的 Fulfillment 状态/账本语义与包裹一致。

## 2. 方案对比与选型

| 方案 | 说明 | 权衡 |
|---|---|---|
| **A. 包裹聚合驱动 + 自定义订单进程（推荐）** | `OrderPackageService.transition` 成功后按包裹聚合回写订单状态；自定义 `OrderProcess` 新增 `Completed` 并禁用 `checkFulfillmentStates`；self 包同步镜像 fulfillment 状态 | **单一权威驱动**（包裹聚合），self/city 统一；业务规则（全送达才 Delivered）由聚合逻辑承担，不丢；core fulfillment 镜像保证后台一致性 |
| B. 仅镜像 fulfillment 让 core 联动 | 让 core 的 fulfillment→order 逻辑自然驱动订单 | city 包无 fulfillment 无解；且需给 city 包伪造 fulfillment，破坏语义 |
| C. 新增独立 order-closure 插件 | 履约闭环逻辑放新插件 | 与 OrderPackageService 强耦合、文件分散；沿用既有 LogisticsPlugin 更内聚 |

**选型：方案 A**。理由：OrderPackage 已是逐包状态权威载体，由其聚合出订单状态是唯一能同时覆盖 self/city 的统一口径；自定义订单进程是加 `Completed` 与绕开 fulfillment 守卫的必要手段；镜像 fulfillment 仅作 core 一致性补充（不承担订单状态驱动职责，避免双驱动）。

## 3. 设计详述

### 3.1 订单聚合回写 `reconcileOrderState`（核心）

位置：`packages/logistics-plugin/src/order-package.service.ts`。

在 `transition()` 落库成功后、状态确实变化时调用 `reconcileOrderState(ctx, orderId)`（幂等/非法流转不触发）。聚合规则：

```typescript
async reconcileOrderState(ctx, orderId): Promise<void> {
    const packages = await this.findByOrder(ctx, orderId);
    const hasPending = packages.some(p => p.status === 'pending');
    const shippedCount = packages.filter(p => p.status === 'shipped').length;
    const deliveredCount = packages.filter(p => p.status === 'delivered').length;
    const cancelledCount = packages.filter(p => p.status === 'cancelled').length;

    let target: OrderState | null = null;
    if (deliveredCount > 0 && packages.every(p => p.status === 'delivered')) {
        target = 'Delivered';          // 全部送达
    } else if (deliveredCount > 0) {
        target = 'PartiallyDelivered'; // 部分送达
    } else if (!hasPending && shippedCount > 0 && packages.every(p => p.status !== 'pending')) {
        target = 'Shipped';            // 全部发货（含 cancelled）
    } else if (shippedCount > 0) {
        target = 'PartiallyShipped';   // 部分发货
    }
    // 全部 cancelled：不推进（订单级取消是独立语义，已发货/送达包取消走售后）
    if (!target) return;

    const order = await this.orderService.findOne(ctx, orderId);
    if (!order || order.state === target) return;
    const next = this.orderService.getNextOrderStates(order);
    if (!next.includes(target)) { Logger.warn(...); return; }
    const result = await this.orderService.transitionToState(ctx, orderId, target);
    if (isGraphQlErrorResult(result)) { Logger.warn(...); return; }
    if (target === 'Delivered') await this.markDeliveredAt(ctx, orderId); // 写 Order.fulfillmentDeliveredAt（首次）
}
```

设计要点：
- **target 推导语义**：只有「包裹聚合」判定才推进订单状态；`getNextOrderStates` 二次过滤防止非法流转（如 Shipped 已终态再被部分送达拉回）。
- **all-cancelled 不推进**：与阶段6 边界一致（订单级取消走订单语义，不回写包裹）。
- `markDeliveredAt`：订单首次进入 `Delivered` 时写 `Order.fulfillmentDeliveredAt` 自定义字段（自动交易完成的扫描基准，见 3.4）。

### 3.2 自定义订单进程（`Completed` + 禁用 `checkFulfillmentStates`）

新建 `packages/logistics-plugin/src/order-completion.process.ts`：

```typescript
declare module '@vendure/core' {
    interface OrderStates {
        Completed: never;
    }
}

export const orderCompletionProcess: OrderProcess<OrderState> = {
    transitions: {
        Delivered: { to: ['Cancelled', 'Completed'] },   // 合并到默认进程
    },
};
```

在 [plugin.ts#L194](file:///d:/zhao/vendure/packages/logistics-plugin/src/plugin.ts#L194) `configuration` 钩子中注册（幂等防重复）：

```typescript
import { configureDefaultOrderProcess } from '@vendure/core';
// 幂等：仅当 process 未被本插件改写时注入
if (!(config.orderOptions.process ?? []).some(p => (p as any).__logisticsClosure)) {
    config.orderOptions.process = [
        configureDefaultOrderProcess({ checkFulfillmentStates: false }),
        { ...orderCompletionProcess, __logisticsClosure: true } as any,
    ];
}
```

- **禁用 `checkFulfillmentStates` 的必要性**：city 包无 fulfillment，core 的 fulfillment 状态校验会拦截订单转 Shipped/Delivered；业务规则改由 `reconcileOrderState` 承担（全送达才 Delivered），不丢规则。
- `Completed` 通过 `OrderStates` 接口增强并入 `OrderState` 联合类型；`mergeTransitionDefinitions` 会把 `Delivered: {to:['Cancelled','Completed']}` 与默认 `Delivered: {to:['Cancelled']}` 并集。
- `__logisticsClosure` 标记用于幂等检测（configuration 钩子可能多次执行）。

### 3.3 Fulfillment 镜像（self 包，core 一致性）

在 `OrderPackageService.transition()` 内，包裹状态变化后，若该包有 `fulfillmentId` 且目标为 shipped/delivered，调用 `orderService.transitionFulfillmentToState` 把 fulfillment 转到对应状态：

| 包裹状态 | fulfillment 目标 |
|---|---|
| shipped | `Shipped` |
| delivered | `Delivered` |

- 镜像**失败仅告警**，不阻断包裹流转与订单聚合。
- core 的 `handleFulfillmentStateTransitByOrder` 在镜像时也会尝试推订单状态——**幂等不冲突**（同样受 `getNextOrderStates` 约束）；`reconcileOrderState` 仍是唯一权威驱动。
- 好处：admin 后台 Fulfillment 状态/历史与包裹一致，Sale 账本语义完整。

### 3.4 交易完成 `Completed`（手动 + 自动）

**手动确认收货**：
- admin mutation `completeOrder(orderId: ID!): Boolean!`（权限 `Permission.UpdateOrder`）→ `transitionToState(orderId, 'Completed')`；幂等（已完成返回 true）。
- C端 shop mutation `confirmOrderReceipt(orderId: ID!): Boolean!`：归属校验（`customer.user.id === activeUserId`，复用阶段7 模式）→ `transitionToState('Completed')`；幂等。

**自动交易完成**：
- 新增 `Order.fulfillmentDeliveredAt` 自定义字段（timestamp，nullable，public，见 [catalog-custom-fields.ts](file:///d:/zhao/vendure/packages/logistics-plugin/src/catalog-custom-fields.ts#L49-L100)），在订单首次进入 `Delivered` 时写入。
- 新建 `OrderCompleteAutoService`（或方法）`scanForAutoComplete(ctx, now)`：扫描 `state='Delivered' AND fulfillmentDeliveredAt <= now - completeDays` 的订单 → `transitionToState('Completed')`。
- `ScheduledTask` `order-complete-auto`（每 5 分钟，复用 OrderTimeoutPlugin 的补偿扫描模式，在 configuration 钩子幂等注册到 `schedulerOptions.tasks`）定时调 `scanForAutoComplete`。
- admin mutation `runAutoCompleteScan(): Int!` 供运营/e2e 手动触发，返回本次完成订单数。
- 完成天数：`LogisticsPlugin.init({ defaultCompleteDays })` 兜底 + Channel 自定义字段 `orderCompleteDays`（整数，可空）覆盖（与 OrderTimeoutPlugin 的 per-channel 覆盖风格一致）。

### 3.5 与既有 OrderTimeoutPlugin 的协同（不重复实现）

| 已有机制 | 触发 | 说明 |
|---|---|---|
| `RECEIPT` 超时（Shipped 后 N 天 → Delivered 自动签收） | 订单 → `Shipped` | **履约闭环使订单到 Shipped 后该机制自动生效**，本期不重复实现 |
| `FULFILLMENT` 超时提醒 | 支付 Settled | 已存在，与本期正交 |
| `REVIEW` 评价提醒 | 订单 → `Delivered` | 已存在，与本期正交 |

本期只新增：`Delivered → Completed` 的自动交易完成（`Completed` 是本 fork 此前不存在的状态）。

### 3.6 错误处理 / 幂等 / 边界

| 场景 | 行为 |
|---|---|
| 包裹聚合目标不在 `getNextOrderStates` | 告警 + 跳过，不抛错不阻断主链路 |
| `transitionToState` 返回错误 | 告警 + 跳过 |
| 包裹状态幂等（重复事件） | `transition` 提前返回，不触发 reconcile |
| fulfillment 镜像失败 | 告警 + 不阻断 |
| 已完成订单再 `completeOrder`/`confirmOrderReceipt` | 幂等返回 true |
| 自动扫描遇已完成/已取消订单 | 状态过滤跳过 |
| `Completed` 回退 | 状态机天然无出边，不可回退 |
| 全部包裹 cancelled | 不推进订单状态（订单级取消独立语义） |
| 历史订单数据回填 | 不做 |

## 4. 数据流示例

```
下单拆两仓(B5/A3) → confirmSplitPlan → P1(pending)/P2(pending)；订单 PaymentSettled

P1 发货 → batchCreateFulfillment(P1)
  → P1.shipped + fulfillment#1 → Shipped（镜像）
  → reconcile：部分发货 → 订单 PartiallyShipped

P2 转同城 → createDelivery(P2) → P2.shipped + deliveryOrderId 回填
  → reconcile：全部发货（无 pending）→ 订单 Shipped
  → （可选）OrderTimeoutPlugin RECEIPT 生效：N 天后自动签收 Delivered

P1 送达 → markPackageDelivered(P1) → P1.delivered + fulfillment#1 → Delivered（镜像）
  → reconcile：部分送达 → 订单 PartiallyDelivered

P2 配送送达 → mockDeliveryEvent/达达 webhook(delivered) → P2.delivered
  → reconcile：全部送达 → 订单 Delivered + fulfillmentDeliveredAt 置位

确认收货（C端按钮 confirmOrderReceipt / admin completeOrder）
  → 订单 Completed
或 自动：Delivered 后 N 天未确认 → order-complete-auto 扫描 → 订单 Completed
```

## 7. 成功标准

1. 拆单订单随包裹状态聚合自动推进：`PartiallyShipped → Shipped → PartiallyDelivered → Delivered`。
2. city 包（无 fulfillment）同样驱动订单状态，不被 `checkFulfillmentStates` 拦截。
3. self 包 fulfillment 状态镜像（shipped/delivered），后台与包裹一致。
4. 手动确认收货（admin `completeOrder` / C端 `confirmOrderReceipt`）使订单 → `Completed`，幂等。
5. 自动交易完成：Delivered 超过 N 天（可 Channel 覆盖）→ `Completed`，`runAutoCompleteScan` 可手动触发验证。
6. `Completed` 不可回退；非法流转/错误仅告警不阻断主链路。
7. 全量回归 9+1 套 e2e 全绿。
