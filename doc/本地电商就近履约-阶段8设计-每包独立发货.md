# 本地电商就近履约 · 阶段8设计：每包独立发货（按包行过滤 fulfillment）

> 承接：阶段5（OrderPackage 实体持久化）边界项之「每包独立 fulfillment：`batchCreateFulfillment` 按包行过滤发货（当前为整单发货，一次发货回填一个包）」。
> 目标：将发货语义从「整单发货（一次 fulfillment 覆盖订单全部行）」升级为「按包发货（每个 fulfillment 只覆盖该包的行明细）」，使同一订单的多个包裹可分仓、分批发货，账本逐仓准确落账。

## 1. 背景与要解决的问题

当前 [batchCreateFulfillment](file:///d:/zhao/vendure/packages/logistics-plugin/src/logistics.service.ts) 的每项发货都是把**订单全部行**传给 `orderService.createFulfillment`，`packageId` 仅用于事后按包回填（挂钩点2 回填 `fulfillmentId` + 实际运费）。这带来两个问题：

- **同单多包无法分批发货**：若同一订单先后给 P1、P2 各创建一次 fulfillment，第二次会因行已被首次 fulfillment 覆盖（Vendure 校验「行已全部履约」）而失败；即使不失败，也会造成重复的库存扣减与账本 Sale。
- **账本无法逐仓反映**：整单发货时 core 一次把全部 allocation 转 Sale，多个仓的账本在同一时间点齐落，无法表达「P1 先发、P2 后发」的真实履约节奏。

阶段5 已把拆单包持久化为 `OrderPackage`（含 `linesJson` = `[{ orderLineId, quantity }]`，在 `confirmSplitPlan` 时落库），**按包行数据已具备**，只差发货时按包过滤。

## 2. 方案对比与选型

| 方案 | 说明 | 权衡 |
|---|---|---|
| **A. 按包为主 + 整单降级（推荐）** | `batchCreateFulfillment` 有 `packageId` 且 `linesJson` 非空 → 只发该包行；无 `packageId` 或 `OrderPackage`/`linesJson` 缺失 → 降级整单发货（告警不阻断） | **单入口自适应**：拆单订单按包、非拆单订单整单，调用方无需选择；无重复逻辑；数据缺失优雅降级兼容旧行为 |
| B. 强制按包 | 一律要求 `packageId` 且 `linesJson` 存在，缺失即报错 | 一致性最强，但非拆单订单无法走该入口，破坏向后兼容（phase3 t7 等旧场景） |
| C. 新增独立方法 | `batchCreateFulfillment` 保持整单不动，另加 `createPackageFulfillment` 按包发货 | 两条 fulfillment 路径并行，发货逻辑分叉、调用方需自行判断入口，表面积更大 |

**选型：方案 A（按包为主 + 整单降级）**。理由：能满足客户多样化需求（分仓分批 vs 单仓整单）而无需区分入口；单条 fulfillment 创建路径便于统一维护与测试；缺失数据降级不阻断主链路（与既有容错语义一致）。

## 3. 设计详述

### 3.1 核心逻辑改造（`batchCreateFulfillment`）

位置：`packages/logistics-plugin/src/logistics.service.ts`。

将现有「整单行」推导替换为「按包优先」：

```typescript
// 现有（整单行）：
const lines = order.lines.map(l => ({ orderLineId: l.id, quantity: l.quantity }));

// 改为：
let lines: Array<{ orderLineId: ID; quantity: number }>;
if (item.packageId) {
    const pkg = await this.orderPackageService?.findByOrderAndCode(ctx, item.orderId, item.packageId);
    const pkgLines = pkg?.linesJson ? JSON.parse(pkg.linesJson) : [];
    if (pkg && pkgLines.length > 0) {
        lines = pkgLines;                       // 按包行发货
    } else {
        lines = order.lines.map(l => ({ orderLineId: l.id, quantity: l.quantity }));  // 降级整单
        Logger.warn(`包 ${item.packageId} linesJson 缺失，降级整单发货`, loggerCtx);
    }
} else {
    lines = order.lines.map(l => ({ orderLineId: l.id, quantity: l.quantity }));      // 非拆单整单
}
```

- 前提：`OrderPackageService` 新增 `findByOrderAndCode(ctx, orderId, code)`（按 `orderId + code` 查单个包裹，供本方法与既有 `linkFulfillment`/`transition` 复用）。
- 挂钩点2（`linkFulfillment` 回填 `fulfillmentId`/实际运费 + `transition('shipped')`）保持不变，仍按 `orderId + packageId` 精确匹配。
- 无 schema / resolver / 实体改动：`BatchFulfillmentItem.packageId` 已存在，admin 调用方式不变。

### 3.2 错误处理

| 场景 | 行为 |
|---|---|
| 有 `packageId` 但 OrderPackage 查不到（如未拆单确认） | 告警 + 降级整单发货，不阻断 |
| `linesJson` 为空 / JSON 解析失败 | 告警 + 降级整单发货，不阻断 |
| 行已全部履约（如重复发货该包） | `createFulfillment` 返回错误 → 现有 try/catch 捕获，该项 `success=false` + error，不中断批次 |
| `linkFulfillment` / `transition('shipped')` 失败 | 现有 try 块已包裹，仅告警不阻断发货 |

不做额外数量校验（YAGNI）：`linesJson` 由拆单确认时保证恰好划分订单行数量，超量由 Vendure 校验并返回错误，捕获即可。

### 3.3 幂等 / 边界

| 场景 | 行为 |
|---|---|
| 非拆单订单（无 OrderPackage）发货 | 不带 `packageId` 走整单发货，行为与阶段3 一致 |
| 同一包重复发货 | 第二次 `createFulfillment` 因行已履约返回错误 → `success=false`，OrderPackage 不被重复回填 |
| 包内行数量 ≠ 订单行剩余量 | Vendure 校验并返回错误，捕获后该项失败，不影响其他项 |
| 历史/既有 behavior | 带 `packageId` 的单包发货场景（phase5/6/7 e2e 仅发一包）断言不变：对应包 shipped+fee 回填、他包仍 pending |

## 4. 数据流示例

```
下单拆两仓(B5/A3) → confirmSplitPlan
  → OrderPackage P1(pending, B/5, linesJson=[{L1,5}]) / P2(pending, A/3, linesJson=[{L2,3}])

P1 先发 → batchCreateFulfillment(packageId=P1, fee=1000)
  → fulfillment#1 仅覆盖 L1×5 → core 仅 B 仓转 Sale → P1 shipped + fulfillmentId + fee=1000；P2 仍 pending
  → 账本：1 条 order:out（B 仓）

P2 后发 → batchCreateFulfillment(packageId=P2, fee=800)
  → fulfillment#2 仅覆盖 L2×3 → core 仅 A 仓转 Sale → P2 shipped + fulfillmentId + fee=800
  → 账本：2 条 order:out（B/A 各一）
```

**新增** `tools/e2e-phase8-per-package-fulfillment.mjs`（复用阶段7 辅助函数模式：客户注册/登录/下单拆两仓/confirmSplitPlan/readOrderFulfillments）：

| 用例 | 场景 | 断言 |

## 7. 成功标准

1. 拆单订单按包发货：`batchCreateFulfillment(P1)` 仅覆盖 P1 行，P2 不受影响仍 pending。
2. 同单多包可分先后发货，各包 fulfillment 行互不相交，行并集 = 订单全部行。
3. 账本逐仓准确：P1 发货后仅 P1 仓一条 Sale，P2 发货后两仓各一条。
4. 非拆单订单整单发货不受影响（降级兼容）。
5. 全量回归 8 套 e2e 全绿。
