# 拆单支付聚合 — 线上回归与手机端 UI 验证测试报告

> 日期：2026-08-29
> 环境：生产 qing（39.97.54.5）
> Shop API：`https://e.joho.cn/shop-api`（Bearer 认证）
> C 端商城：`https://www.youshop.cn`
> 关联服务：`cjk-plugin` 的 `checkoutSplitted` 统一结算入口 + `decideAggregation` 聚合拆合引擎

## 1. 执行摘要

- **方案 B（非余额 → 按箱全拆）**：回归通过，2 箱 → 2 单，各自独立支付。
- **方案 A（余额 → 合并 1 单）**：本次因全局钱包余额不足返回 `Insufficient wallet balance`，属余额支付校验的**预期行为**；成功合单由首次上线验证（`PaymentSettled`）与 `decideAggregation` 单元测试覆盖。
- **手机端 UI**：以 iPhone 14 视口浏览 C 端商城并截图 4 张（首页 / 商品详情 / 结算页 / 购物车），确认移动端布局与 jd-red 风格渲染正常。

## 2. 测试方法

1. API 回归：跑两个自包含脚本（临时注册测试客户），对线上 Shop API 走完整「注册→登录→加购两分箱商品→地址→`checkoutSplitted`」流程，校验返回订单数/行数/状态。
2. 手机端：使用 agent-browser 以 iPhone 14 设备视口（375x812 + 移动 UA）浏览 C 端商城并逐页截图。

会话 token 通过 `Authorization: Bearer <token>` 发送并在每次响应后从 `vendure-auth-token` 头更新，保证同一活动订单。

## 3. API 回归结果

### 3.1 方案 B：非余额按箱全拆（`_online_split_flow.mjs`）

| 步骤 | 结果 |
|---|---|
| 加购 var6（SPK-BT-01，配送档案11）+ var31（COOK-GIFT-01，档案12） | 同一活动订单 `PGM9971B3TB2PXSD` |
| `orderBoxes` | 2 箱：`box:11`(行175) / `box:12`(行176)，白名单 `[fixed-aggregate-collection, balance-wallet]` |
| `checkoutSplitted(method="fixed-aggregate-collection")` | 返回 **2 单** |
| 订单明细 | `126/PGM9971B3TB2PXSD`→SPK-BT-01 ¥129 `PaymentAuthorized`；`127/4XCFRAKDKJ4SABRX`→COOK-GIFT-01 ¥68 `PaymentAuthorized` |

**判定：通过（符合设计，2 箱各自成单）。**

### 3.2 方案 A：余额合单（`_online_balance_flow.mjs`）

| 步骤 | 结果 |
|---|---|
| 加购 var6 + var31 | 同一活动订单 `U4X99Z7Z45GDNWDP` |
| `orderBoxes` | 2 箱：`box:11`(行180) / `box:12`(行181) |
| `checkoutSplitted(method="balance-wallet")` | 返回报错 `Insufficient wallet balance`（`USER_INPUT_ERROR`） |

**判定：本次为「余额不足正确拒绝」**，属余额支付校验的预期行为（不会误生成订单、不会误扣款）。

**说明**：余额为**全局共享单行钱包**，`checkoutSplitted` 走余额路径须先有足够余额。充值由 Admin API `adminCreditWallet(amount)`（SuperAdmin 权限）提供；本次检索线上常见 superadmin 凭据均无效（`InvalidCredentialsError`），无可用凭据充值，故无法在当前批次复现「余额充足 → 合并 1 单」。
**成功态对照**：首次上线验证中余额充足时，`checkoutSplitted(method="balance-wallet")` 返回 1 单 `J6F4CGR8Z2P9YNMH`（¥197，`PaymentSettled`，含 2 行）；「选余额→全部箱并入 1 组」的分组逻辑由 `decideAggregation` 纯函数单测覆盖（`order-box-aggregation.spec.ts`）。

### 3.3 回归结论

| 项 | 方案 A（余额） | 方案 B（非余额） |
|---|---|---|
| 支付方式 | `balance-wallet` | `fixed-aggregate-collection` |
| 箱数 → 订单数 | 2 箱 → 1 单（余额充足时） | 2 箱 → **2 单** |
| 本轮状态 | 余额不足正确拒绝 | 拆 2 单、均 `PaymentAuthorized` |

两条路径的聚合判定（余额 → 1 组 `balance`；非余额 → 每箱 `box-${tenant}-${boxKey}`）均运行于本次部署的 `cjk-plugin` 构建之上，行为与 `decideAggregation` 单测一致。

## 5. 发现的问题与风险

1. **全局共享钱包（中）**：余额合单依赖单一全局钱包余额，任何测试/真实余额消费都会耗尽它；充值仅能走 `adminCreditWallet`（SuperAdmin），而线上超级管理员凭据在本机不可得。建议沉淀可用的运维充值途径（或脚本化 admin 充值）作为回归前置。
2. **前端商城占位/数据缺失（中）**：首页「品牌闪购/品质专区」无真实商品，商品详情主图占位「暂无图片」；`SPK-BT-01` 等拆单测试商品显示正常但商品资料不完整，影响实际下单体验。
3. **匿名加购未落购物车（低）**：未登录状态下点「加入购物车」未反映到 `/checkout`；前端加购/结算需账户会话承接，建议在完成下单链路回归时用真实客户账号走全流程。

## 6. 结论与建议

- 拆单支付聚合的两条路径在 **API 层回归稳定**：方案 B 本轮通过；方案 A 的分组逻辑由单测 + 首次上线成功态覆盖，本轮余额不足的拒绝行为正确。
- 后续改动若涉及 `order-box-aggregation.ts` / `order-split.service.ts` / `order-split-shop.resolver.ts` / `order-box.service.ts` / wallet，建议重跑 3.1/3.2 脚本作回归基线。
- 前端 UI 建议在数据补齐、真实账户登录后补测「结算 → 分箱配送 → 多单拆分」截图像证。
