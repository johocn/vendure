# 阶段22 · 设计（结算/下单时运费计算与范围联动）

依据：阶段21 `address-plugin`（`DeliveryAddress` 地址簿 + `DeliveryRange` 按店配送范围 + `DeliveryService.validateDelivery`）。

核心：在既有 `@vendure/address-plugin` 内扩展「运费计算 + 配送范围联动」，实现 结算拦截（hard gate）+ 加购预检（advisory）。店铺归属沿用现网 `Product.shopId` 反查，不建 OrderLine.shopId 关联。

## 1. 目标与非目标

**目标**
- 结算时能判定订单涉及店铺在当前收件地址下是否可配送（范围联动），不可达则该配送方式 ineligible，前端提示“部分店铺无法配送”。
- 按店计算运费并聚合为整单运费；支持“满额包邮”阈值。
- C 端提供加购/结算前实时可达性提示与“从地址簿选收货地址并写入订单收件信息”。

**非目标**
- 不做跨店运费分摊的复杂阶梯/分段计价。
- 不改原有 `delivery-plugin`（配送派单），不拆新包。
- 不在下单动作本身强 throw 拦截（结算用 eligibility checker 硬性拦截，加购阶段用查询做 advisory）。

## 2. 数据模型（扩展 `DeliveryRange`）

在 `packages/address-plugin/src/delivery-range.entity.ts` 增加：
- `baseFee`：`int`，默认 `0`，基础运费（分，全站金额口径对齐 core 用整数分）。
- `freeThreshold`：`int nullable`，满额包邮阈值；`null` 表示该店不支持包邮（始终收 baseFee）。
- 均为普通 SQL 列，跨库安全；admin `DeliveryRangeInput` 与 C 端 `DeliveryRange` 类型同步暴露。

## 3. 店铺归属（现有复用）

订单涉及店铺 = 对 `order.lines` 的商品 id 去重 → 查 `Product.shopId`（shop-plugin 在 Product 上的自定义字段）→ 得店铺集合。结算 checker、运费 calculator、C 端预检均用同一 `DeliveryService.getOrderShopIds(ctx, order)` 聚合。

## 4. 收件地址数据流（Order 侧新增 custom fields）

结算校验需要 区码/经纬度，需随收件地址持久化到 `Order`。address-plugin `configuration` 钩子注册 Order custom fields：
- `shippingLng`（float nullable）、`shippingLat`（float nullable）、`shippingProvinceCode`、`shippingCityCode`、`shippingDistrictCode`（varchar nullable）。

C 端 mutation `setOrderShippingFromAddress(deliveryAddressId)`：
- 取当前顾客该 `DeliveryAddress` → 写 `order.shippingAddress`（fullName/phone/province/city/district/detail + line）→ 复制上述 codes/经纬度到 Order custom fields。
- 校验与计算都只消费 Order 上的这份快照，避免再查地址簿（符合 core 的快照语义）。

## 5. 结算拦截（hard gate）`RangeShippingEligibilityChecker`

注册进 `config.shippingOptions.shippingEligibilityCheckers`（仿 logistics-plugin 注册 calculator 的方式）。
`check(ctx, order)`：
1. 无 `order.shippingAddress` 或未设置 → 返回 true（跳过判定，不误拦），由 C 端引导先填地址。
2. `getOrderShopIds` 得店铺 → 取 `Order` custom fields（区码/经纬度）构造地址输入 → `DeliveryService.validateDelivery` 逐店校验。
3. 任一店 `inRange=false` → 返回 false（整单该配送方式不可用）。
4. 全部可达 → true。

## 6. 运费计算 `RangeShippingCalculator`

注册进 `config.shippingOptions.shippingCalculators`。`calculate(ctx, order)`：
1. `getOrderShopIds` 得店铺；按店取 `DeliveryRange`。
2. 某店运费 = 该店订单行小计（`order.lines` 按 product→shopId 分组求和）≥ freeThreshold ⇒ 0（包邮），否则 = baseFee。
3. 整单 `price` = Σ 各店运费；`priceIncludesTax` 取 config；`taxRate` 0。
4. 返回 `metadata: { shops: [{ shopId, subtotal, fee, baseFee, freeThreshold, inRange? }] }`。

## 7. 加购/结算前预检（advisory，C 端）

- `activeOrderDeliveryStatus` @Query（Public 或 Authenticated）：对当前 active order，若已设收件地址，返回各涉及店铺 `{ shopId, inRange, reason }` + 整单 `deliverable`。供前端在结算前实时展示每店可达性（复用 `validateDelivery`）。
- 不做事件订阅 throw 拦截（加购时可能未设地址，避免误拦）；可达性硬性由结算 checker 把关。

## 8. 错误处理

- 地址未设：checker 跳过（返回 true）；预检返回 `deliverable=false`，reason `NO_ADDRESS`。
- circle 缺坐标：`NO_COORDINATES`；district 无码：`NOT_IN_RANGE`。
- 店铺无范围/未启用：`NO_DELIVERY` → 该店不可达。
- 金额均为整数分；除零/空店铺集防御：无店铺订单 → price 0 且 check true。

## 9. 测试（e2e，≥12）

复用 address-plugin e2e 骨架，plugins `[ShopPlugin.init({}), AddressPlugin.init({})]`。覆盖：
1. upsert `DeliveryRange` 带 baseFee/freeThreshold 持久化并可读回
2. 单店 baseFee 求和
3. freeThreshold 满额包邮该店免运费
4. freeThreshold null 始终收 baseFee
5. 多店混合：A 可达收 baseFee、B 满额包邮 → 总运费=A baseFee
6. eligibility 不可达某店 → 该配送方式 ineligible（结算拦截）
7. eligibility 全部可达 → eligible
8. 地址未设 → eligibility 跳过（true）
9. `activeOrderDeliveryStatus` 返回逐店 inRange/reason + 整单 deliverable
10. `setOrderShippingFromAddress` 写 shippingAddress + Order custom fields（区码/经纬度）
11. circle 距离联动：近可达、远不可达，并同步影响 eligibility
12. calculator metadata 含 per-shop 明细
13. 无店铺空订单 → price 0、check true（防御）

## 10. 风险与前置依赖

- 依赖 `Product.shopId`（shop-plugin）→ 需商品已归属店铺；e2e 用 `createShop + assignProductsToShop` 准备数据。
- ShippingMethod 需在 admin 侧以本 checker+calculator 创建，e2e 用 adminClient 建 shipping method（携带本 calculator/checker code）验证结算集成。
- Order custom fields 注册随 `configuration` 钩子生效，无需迁移（customFields 走 core）。
