# 阶段13 · 拼团闭环（Group Buy Closure）设计

> 日期：2026-08-21
> 项目：Vendure 本地化电商（d:\zhao\vendure）
> 前置：阶段12（营销促销闭环-优惠券体系）已完成
> 本文档为设计稿，实施见 companion 文件：`2026-08-21-本地电商就近履约阶段13实施计划-拼团闭环.md`

## 1. 背景与目标

阶段12 已补齐**优惠券**（发券-领券-结算核销-回退），价格促销工具箱拥有：秒杀 + 优惠券。但「多人拼团」（社交裂变、社区团购的核心玩法）仅有**半成品骨架**：

`packages/group-buy-plugin` 已具备实体（GroupBuyActivity / GroupBuyOrder）、管理端 CRUD、开团/参团 mutation、Promotion 条件/动作、过期检查定时任务的雏形，但**业务闭环断裂**：

- `joinGroupBuy` 只登记 GroupBuyOrder 记录，**不写订单 customFields** → 拼团价 Promotion 条件永远不成立，拼团价不生效
- Promotion 条件/动作写死 `args.groupPrice`（需手工配置且每活动不同），无法按当前订单关联的活动动态取价
- 无「成团即结算」联动：成团时未把 pending 参团记录置 success
- e2e 仅 4 个空查询用例，无任何业务流验证

本阶段目标是**打通拼团闭环**，让「开团 → 参团 → 成团 → 结算 → 超时取消/退款」形成可验证的完整链路，并复用阶段12验证过的模式（runtime 注入连接 + condition state 传 action）。

## 2. 范围

### 2.1 目标（In Scope）
1. **拼团价自动生效**：订单携带 `groupBuyActivityId` → Promotion 按活动 `groupPrice` 动态折算拼团价（复用原生结算机制，不改订单状态机）
2. **开团/参团一体**：`joinGroupBuy(activityId, orderId, isLeader)` 校验 → 写订单 customFields（activityId + isLeader）→ 重算价格 → 登记参团 → **原子递增**人数（防超员）
3. **成团结算**：`currentCount >= targetCount` → 活动 `completed`，全部 pending 参团记录置 `success`
4. **满员/窗口校验**：`maxCount` 上限（原子守卫）、未开始/已结束拦截、成团后是否可继续参团（`allowJoinAfterComplete`）
5. **超时未成团**：过期检查（定时任务 + 手动触发 mutation）→ 活动 `expired` → 取消订单 + 退款（Settled 支付）
6. **团长奖励**：leader 订单额外折扣（`leaderRewardType='discount'`；cashback/free 留待后续）
7. **e2e 全链路**：开团价 → 参团价 → 成团 → 满员拦截 → 过期取消退款

### 2.2 非目标（Out of Scope）
- 团长奖励 `cashback`（返现）与 `free`（免单）：涉及独立状态机与副作用，保持 TODO
- 每活动多「团」模型（Pinduoduo 式：团长各自拉 3 人成一组）：本阶段采用**活动级总人数成团**（与现有实体/骨架一致）
- 成团后再拆单/改价等复杂交互
- 与优惠券的叠加规则

## 3. 领域模型（沿用现有实体，仅补逻辑）

```
GroupBuyActivity (活动)                     GroupBuyOrder (参团记录)
┌──────────────────────────────┐          ┌────────────────────────────┐
│ targetCount  成团目标人数      │          │ groupBuyActivityId         │
│ currentCount 当前参团人数      │1──┐      │ orderId                    │
│ maxCount     上限(0=不限)      │   │      │ isLeader                   │
│ status: active|completed|expired│  └──────│ status: pending|success|failed│
│ groupPrice   拼团价(分)        │          └────────────────────────────┘
│ leaderDiscount 团长额外折扣    │
│ leaderRewardType              │
│ allowJoinAfterComplete        │
│ variantId / productId         │
└──────────────────────────────┘
```

Order 自定义字段（沿用现有）：
| 字段 | 类型 | 说明 |
|------|------|------|
| `groupBuyActivityId` | int | 关联的拼团活动 ID（结算时 Promotion 据此取价） |
| `groupBuyIsLeader` | boolean | 是否团长订单 |

## 4. 核心机制

### 4.1 结算闭环（复用原生 Promotion 结算）
```
结算：
  shop: joinGroupBuy(activityId, orderId, isLeader)
    → 校验活动/窗口/满员 → 写 order.customFields.groupBuyActivityId + groupBuyIsLeader
    → orderService.applyPriceAdjustments 自动重算 promotions（无需手动触发）
价格套用：
  group_buy_discount condition: order.customFields.groupBuyActivityId 非空
    → 运行时查 GroupBuyActivity → 校验 active/窗口/含拼团变体行
    → 返回 state { variantId, groupPrice }
  group_buy_price action: 命中拼团变体行 → 折扣 = 原价 - groupPrice
团长奖励：
  group_buy_leader_reward condition: isGroupBuyLeader && 活动存在
    → 返回 state { variantId, leaderDiscount }
  group_buy_leader_reward action: 命中拼团变体行 → 额外 -leaderDiscount
```

**关键点**：Promotion 条件/动作需要访问 DB 取活动配置（groupPrice/leaderDiscount/variantId），沿用阶段12 `coupon-runtime.ts` 模式——`onApplicationBootstrap` 注入 `TransactionalConnection` 到模块级变量，供静态构造的 condition/action 延迟获取（PromotionCondition.check 与 PromotionItemAction.execute 均支持 async）。

**Promotion 配置**：管理端创建**两张**促销（每张单条件+单动作，与优惠券一致）：
1. 「拼团价」= `group_buy_discount` 条件 + `group_buy_price` 动作
2. 「拼团团长折扣」= `group_buy_leader_reward` 条件 + `group_buy_leader_reward` 动作

两张促销的 condition/action 均**无参数**（活动配置运行时动态读取），因此无需随活动创建/编辑/删除同步维护促销。

### 4.2 参团人数原子递增（防超员）
仿阶段12 `atomicIncrementClaimed`：
```
UPDATE group_buy_activity
SET currentCount = currentCount + 1
WHERE id = :id
  AND (status = 'active' OR (status = 'completed' AND :allowJoinAfterComplete = true))
  AND startAt <= :now AND endAt >= :now
  AND (maxCount = 0 OR currentCount < maxCount)
```
受影响行数 = 0 → 满员/不可参 → 抛错回滚（不写订单字段）。

**幂等**：同一 `orderId` 重复 join 同一活动 → 仅更新 `isLeader` 与订单字段，不重复递增。

### 4.3 成团 / 过期
- **成团**：递增后 `currentCount >= targetCount` → 活动置 `completed`，该活动全部 pending 参团记录置 `success`（成团即结算）
- **allowJoinAfterComplete**：活动已 completed 且允许继续加入 → 新参团记录直接置 `success`
- **过期**：`endAt` 已过且未成团 → 定时任务/手动检查 → 活动置 `expired` → 逐个取消订单（`cancelOrder`）+ 对 Settled 支付退款（`createRefund`）→ 参团记录置 `failed`

## 5. 状态机

```
活动（GroupBuyActivity.status）：
 active ──(currentCount >= targetCount)──► completed
   │                                          ▲
   │ (endAt 已过, 未成团)                      │ (allowJoinAfterComplete 续参)
   ▼                                          │
 expired

参团记录（GroupBuyOrder.status）：
 pending ──(活动成团)──► success
    │
    │ (活动过期未成团)
    ▼
 failed
```

## 6. API 变更

### Shop
- `joinGroupBuy(activityId, orderId, isLeader): GroupBuyOrderResult` —— **语义升级**：不再是纯登记，而是「开团/参团一体」：校验+写订单字段+重算价格+登记+原子递增。返回含新状态

### Admin
- 新增 `runGroupBuyExpiryCheck(): Boolean!` —— 手动触发过期检查（等价定时任务 `group-buy-check` 的逻辑），供运营兜底与 e2e 确定性触发

## 7. e2e 场景

1. **开团全链路**：建活动（targetCount=3, groupPrice < 原价）→ leader 加购 → joinGroupBuy(isLeader=true) → 订单价 = 拼团价 + 团长折扣 → 支付成功
2. **参团价**：member 加购 → joinGroupBuy(isLeader=false) → 订单价 = 拼团价（无团长折扣）
3. **成团**：第3人加入 → 活动 completed，全部参团记录 success
4. **满员/成团拦截**：新活动 maxCount=2 → 第3人加入被拒；allowJoinAfterComplete=false 时已成团活动拒绝加入
5. **过期未成团**：加入并支付后，admin 把 endAt 改为过去 → 触发 `runGroupBuyExpiryCheck` → 活动 expired、订单 Cancelled、Refund Settled、参团记录 failed
6. **校验拦截**：未开始/已结束不可加入；订单不含拼团变体不可加入

## 8. 风险与注意

- **注册即参团**：人数在 join 时递增（非支付成功时），未支付参团也计入人数——与现有骨架一致；活动过期清理会取消并退款，未支付订单取消无副作用。文档明确此模型
- **PromotionItemAction 读 state**：已确认 core `promotion.entity.ts` 将 condition 返回值按 code 嵌套传入 item action 的 `state`（与阶段12 coupon 同款）
- **并发递增**：原子 UPDATE 保证不超员；count 与订单字段写入非同一事务，递增成功后写字段失败仅导致人数多计（低概率，可接受；活动过期清理兜底）
- **priceIncludeTax**：结算基准以 `ctx.channel.pricesIncludeTax` 为准（unitPriceWithTax / unitPrice），与 coupon 一致
