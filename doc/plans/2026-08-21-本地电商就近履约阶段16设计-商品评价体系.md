# 阶段16 · 商品评价体系（交易后评价闭环）设计

> 承接：本地电商就近履约方案（阶段15 会员积分闭环已上线）
> 目标：在现有 review-plugin 基础上补齐 C 端完整评价闭环——**追评 / 修改 / 删除 / 评星驱动商品评分聚合 / 屏蔽刷评 / 匿名**，构建真实口碑数据。

## 1. 背景与现状

`packages/review-plugin` 已具备基础能力（源自 Vendure 官方 review 插件的移植）：

- **C 端**：`createReview`（仅登录用户、订单需 `Delivered/Completed`、每条 orderLine 至多一条）、`productReviews`（仅 approved）、`myReviews`、`reviewStats`、`markHelpful`。
- **管理端**：`reviews` / `review` / `reviewStats` 列表查询，`replyReview` / `approveReview` / `rejectReview`（pending→approved/rejected 审核流）。
- 实体 `Review`：customerId / productId / orderLineId / variantId / rating / content / images / videos / tags / isAnonymous / status / reply / repliedAt / helpfulCount。

阶段16 在保留既有能力的前提下，补齐真实电商评价闭环的缺口：

| 能力 | 现状 | 阶段16目标 |
|---|---|---|
| 追评（追加评价） | ❌ 无 | 主评下追加多条追评，聚合只统计主评 |
| 修改评价 | ❌ 无 | 作者可改本人 pending/approved 评价 |
| 删除评价 | ❌ 无 | 作者可删本人评价（软删，聚合排除） |
| 评星驱动商品评分聚合 | ⚠️ 仅运行期实时算 reviewStats | 聚合结果写入 Product.rating / reviewCount |
| 屏蔽刷评 | ⚠️ 订单状态+一单一评+审核流 | 增加内容最小长度、前后端双重归属校验 |
| 匿名 | ✅ isAnonymous | 保留；匿名仅脱敏展示，评分正常计入聚合 |

## 2. 核心设计决策

### 2.1 追评采用「自关联 parentId」而非新增独立实体
- `Review` 增加自关联 `parent / followUps`（`parentId` FK）。
- 追评仍是 `Review`，但 `parentId` 指向主评；**聚合与商品列表永远只取主评（`parentId IS NULL`）**。
- 追评不支持再追评（深度=1），避免递归复杂度。
- 追评拥有独立 content/images/videos/tags，rating 可选（可仅文字追评）；评分聚合不受追评影响。

### 2.2 评星驱动商品评分聚合——Product 自定义字段
- `Product` 注册 `rating`（float，一位小数）+ `reviewCount`（int）两个 public 自定义字段。
- 在**影响评分的时机**统一重算：`createReview`(autoApprove 时) / `approveReview` / `updateReview`(approved 变更) / `deleteReview`(approved 删除) / `rejectReview`。
- 重算口径与 `reviewStats` 一致：**只统计 `status='approved'` 且 `parentId IS NULL`** 的主评；平均值保留一位小数（`Math.round(avg*10)/10`）。
- C 端 `productRating(productId)` 直读 Product 自定义字段，供列表卡片展示，避免每次都扫全表。

### 2.3 屏蔽刷评（fake-review）
- **强校验**（createReview 内，前端无法绕过）：
  - 必须 `ctx.activeUserId` 存在且能解析到 Customer。
  - `rating ∈ [1,5]` 整数、`content` 去空白后非空。
  - `orderLineId` 必须指向**当前用户自己的订单行**，且该订单处于 `Delivered/Completed`。
  - 同一 `(orderLineId, customerId)` 只允许一条主评（现有逻辑保留）。
  - content 去除首尾空白；`ReviewPluginOptions.minContentLength`（默认 0）低于阈值直接拦截。
- **审核流**：新建主评/追评默认 `pending`，经 `approveReview` 后对外可见并计入聚合（未开启 autoApprove 时）；`rejectReview` 拒绝对外。
- **配置**：`ReviewPluginOptions.autoApprove`（默认 false）开启后新建即 approved 并立即重算聚合，适合信任环境的快速闭环。

### 2.4 归属与权限（防越权改删）
- `updateReview` / `deleteReview` / `createFollowUpReview` 均要求 `customer.user.id === ctx.activeUserId`（沿用阶段7「归属必须用 customer.user.id」教训，用 `findOneByUserId` 解析 Customer 后与 `review.customerId` 比对）。
- `do not rely on customer.id vs user.id`——Review 存 `customerId`（Customer 主键），与服务解析出的 `customer.id` 比对，正确。
- 修改仅限 `pending/approved`；删除将 `status='deleted'`（保留行用于幂等追溯、helpful 计数保留），列表与聚合一律排除 deleted。

### 2.5 状态枚举
- `pending | approved | rejected | deleted`。用字符串列（沿用现有），不引入数据库枚举，降低跨库（sqljs/PostgreSQL）风险。

## 3. 变更清单

### 3.1 实体 `review.entity.ts`
- 新增自关联：`@OneToMany followUps` + `@ManyToOne parent`（FK 列 `parentId`，nullable）。

### 3.2 服务 `review.service.ts`
- 注入 `ProductService`。
- 新增 `createFollowUpReview` / `updateReview` / `deleteReview` / `recomputeProductRating` / `getProductRating` / `getReviewFollowUps`。
- `createReview`：content 去空白 + `minContentLength` 校验；`autoApprove` 时置 approved 并重算评分。
- `approveReview` / `rejectReview` / `updateReview` / `deleteReview`：触达 approved 变化时重算商品评分。
- `getProductReviews` / `getReviewStats`：只取 `approved` 且 `parentId IS NULL`；排除 `deleted`。

### 3.3 GraphQL Schema（plugin.ts）
- **C 端 shopApiExtensions**：
  - `input UpdateReviewInput` / `input FollowUpReviewInput`（含可选 rating、images、videos、tags、isAnonymous、content）。
  - `type ProductRating { rating: Float!, reviewCount: Int! }`。
  - `Review` 增加 `parentId: ID`、`followUps: [Review!]!`。
  - `extend type Query`: `productRating(productId: ID!): ProductRating!`。
  - `extend type Mutation`: `updateReview(id: ID!, input: UpdateReviewInput!): Review!`、`deleteReview(id: ID!): Boolean!`、`createFollowUpReview(reviewId: ID!, input: FollowUpReviewInput!): Review!`。
- **adminApiExtensions**：`Review` 增加 `parentId` / `followUps`；`reviewStats` 沿用；不新增审核 mutation。
- **configuration**：注册 `Product` 自定义字段 `rating` / `reviewCount`（public: true）。沿用 `mergeCustomFields` 幂等并入。

### 3.4 类型 `types.ts`
- `CreateReviewInput` 扩展可选 `rating`（追评可复用）。
- 新增 `UpdateReviewInput` / `FollowUpReviewInput` / `ProductRating`。
- `ReviewPluginOptions` 增加 `minContentLength?: number`、`autoApprove?: boolean`。

### 3.5 工程配套（对齐 flash-sale-plugin）
- 新增 `vitest.config.mts`、`tsconfig.build.json`、`e2e/review.e2e-spec.ts`（含 `e2e/__data__`）。

## 4. 测试策略（e2e）

沿用 SQLite(sqljs) + @vendure/testing，覆盖真实全链路：

1. **插件可加载；Product 字段默认 rating=0/reviewCount=0**。
2. **评价订单商品**：订单 Delivered 后可创建（pending）；未送达订单创建被拦截；同一 orderLine 重复评价被拦截。
3. **审核后对外可见**：approve 后 `productReviews` 出现、`productRating` 更新；未审核不可见。
4. **追评**：对本人主评追加追评，出现在主评 `followUps`；聚合/商品列表不计追评条数。
5. **修改**：作者改评分/内容，聚合随评分重算；非作者改删被 Forbidden；对已审核主评修改后列表内容同步。
6. **删除**：作者删主评后列表/聚合剔除，deleted 不计分。
7. **屏蔽刷评**：content 过短（minContentLength）拦截；他人 orderLine 评价被 Forbidden。
8. **匿名**：isAnonymous 时 `customerName` 返回 null，但评分计入聚合。

## 5. 风险与权衡
- SQLite 实体日期列沿用 `repliedAt?: Date` 写法（阶段11 已实证，勿写死 timestamp/datetime）。
- `simple-json` 列（images/videos/tags）沿用现状；跨库兼容（sqljs + PostgreSQL）已在 review-plugin 现有实现中验证。
- 追评聚合只统计主评，避免出现「销量口碑靠追评刷高」的注水；主评存档为评价基座。
- 软删保留行，删除后 `helpfulCount`/评论 ID 不再对外，但不会造成 FK 断裂。

## 6. 交付与部署
- 工程铁律：本地 `tsc -p packages/review-plugin/tsconfig.build.json` 产出 `lib/` 并入库；服务器 `git pull` + `pm2 restart`，**不在服务器构建**。
- review-plugin 产物 `lib/` 须纳入 git 跟踪。
