# 阶段11 设计文档：退款/售后闭环（Refund After-Sales Closure）

> 日期：2026-08-20
> 前置：阶段10 履约闭环（订单交易完成 Completed）
> 目标：把"售后（after-sales）"与"退款（refund）"真正闭环，直接延续阶段10 的订单 Completed 状态。

## 1. 背景与动机

阶段10 实现了"确认收货 → 订单 Completed"，履约链路已走到终态。但"钱"的链路尚未真正闭合：

- **售后发起时机断层**：用户确认收货后订单进入 `Completed`，而 after-sales-plugin 的 `createRequest` allowedStates 只有 `['Shipped','Delivered','PartiallyDelivered','Cancelled']`，**缺 `Completed`**。在 C 端电商的真实业务里，售后恰恰发生在"确认收货之后"，当前实现导致用户无售后入口。
- **退款结算断层**：`processRefund` 调用 `orderService.refundOrder` 创建 Vendure 原生 `Refund`，但开发用 dummy 支付处理器没有实现 `createRefund`，导致 Refund 一直停在 `Pending` —— **钱没有真正退回去**，只是"假退款"。`AfterSalesRequest.state` 被标记为 `Refunded`，但底层资金从未落账。

## 2. 现状调研结论

### 2.1 Vendure 原生 Refund 体系
- `Refund` 实体状态机：`Pending → [Settled, Failed]`（[default-refund-process.ts](file:///d:/zhao/vendure/packages/core/src/config/refund/default-refund-process.ts)）。
- `OrderService.refundOrder` → `PaymentService.createRefund`：
  - 若 `PaymentMethodHandler` 实现了 `createRefund`，则按其返回的 `{ state, transactionId, metadata }` 推进 Refund 状态机；
  - **若未实现**（如 dummy handler），则 `createRefundResult = false`，Refund 停留在 `Pending`，需人工 `settleRefund`。
- `CreateRefundResult`：`{ state: RefundState; transactionId?: string; metadata? }`。
- 退款金额受单笔支付可退余额约束：`refundableAmount = payment.amount - 已退(非Failed)`. 超额返回 `RefundAmountError`。

### 2.2 现有 after-sales-plugin 能力（已具备，勿重复造）
- C 端：`createAfterSalesRequest`（return_refund / refund_only / exchange）、`cancelAfterSalesRequest`、`updateReturnTracking`。
- 后台：`approve / reject / confirmReturnReceived`（多仓库存回补 `applyAfterSalesRestockMulti` + `restockJson` 留痕）、`processAfterSalesRefund`。
- 状态机：`Pending → Approved → Returning → Received → Refunded`，另有 `Rejected / Closed`。
- 归属校验基于 `customer.user.id`；实体落库后 `hydrate` 重载关系避免 GraphQL 非空字段 报错（已固化）。

### 2.3 达达计费
退款针对的是"商品款"，与达达"配送费"（`DeliveryOrder` 计费）是两个独立账目，本阶段不涉及达达配送费的退款（配送费在履约/取消环节已处理）。

## 3. 核心设计：三处闭环缺口

### 3.1 缺口A：Completed 售后入口（阶段10 打通）
- `createRequest` allowedStates 加入 `'Completed'`。
- 售后期起始基准切换到订单进入 Completed / Delivered 的时间，而非 `updatedAt`：新增订单自定义字段 `fulfillmentCompletedAt`（阶段10 的 `fulfillmentDeliveredAt` 旁），确认收货时落库，作为"售后期"计时的权威起点。
- 窗口规则（保持现有）：`无理由 maxDaysAfterDelivery`(默认7) + 质量兜底15 → 上限 22 天。沿用 `options.maxDaysAfterDelivery`。

### 3.2 缺口B：退款结算闭环（钱真正退回）
- **dummy 支付处理器**补 `createRefund`（开发/测试环境用）：返回 `{ state: 'Settled', transactionId }`，使虚拟订单退款能走到 Settled 终态。
- **after-sales `processRefund` 强化**：
  1. 调 `refundOrder` 创建 Refund；
  2. 若返回 Refund 停在 `Pending`（真实网关异步对账场景），追加 `settleRefund`，使其达到 `Settled` 终态；
  3. 仅当 Refund 达 `Settled` 才把 `AfterSalesRequest.state → 'Refunded'`；若退款失败/Failed，转入 `RefundFailed`（新增状态），可重试，杜绝"假退款"。
- 落库字段：`refundTransactionId`、`actualRefundAmount`、`refundedAt`。

### 3.3 缺口C：退款偏重校验（部分退款）
- `processRefund` 校验：实退金额 ≤ 该订单对应可退余额；`refundAmount` ≤ 订单剩余可退（含部分售后已退）。防止一单多退超卖退款。

## 4. 数据模型变更

### 4.1 after-sales 实体新增列
| 字段 | 类型 | 说明 |
|---|---|---|
| `refundTransactionId` | varchar nullable | 支付网关退款流水号 |
| `actualRefundAmount` | int nullable | 实际退款到账金额 |
| `refundedAt` | timestamp nullable | 退款完成时间 |
| `refundError` | text nullable | 退款失败原因（RefundFailed 留痕） |

### 4.2 订单自定义字段新增
| 字段 | 类型 | public | 说明 |
|---|---|---|---|
| `fulfillmentCompletedAt` | datetime | true | 确认收货（进入 Completed）时间，作为售后期起点 |

### 4.3 状态机扩展（after-sales）
`Received → [Refunded, RefundFailed]`，`RefundFailed → [Refunded]`（重试）。其余不变。

## 5. API 面
- **C 端已具备**：create / cancel / updateReturnTracking / myAfterSalesRequests / afterSalesRequest。
- **后台新增/微调**：`retryAfterSalesRefund(id)`（RefundFailed 重试退款），其余 approve / reject / confirmReturnReceived / processAfterSalesRefund 不变，SD 类型补 `refundTransactionId / actualRefundAmount / refundedAt / refundError`。

## 6. 流程总览
```
订单 Shipped/PartiallyDelivered/Delivered/Completed
   │  用户「确认收货 / 自动完成」→ Completed（落 fulfillmentCompletedAt）
   ▼
createAfterSalesRequest(type, reason, refundAmount)
   ▼  Pending
approve / reject
   ▼  Approved → （return_refund 走退货）/ （refund_only 可直接到 Received）
updateReturnTracking → Returning
   ▼
confirmReturnReceived(实收数量) → 多仓库存回补 → Received
   ▼
processAfterSalesRefund → refundOrder → [settleRefund] → Refund=Settled → Refunded ✓
   （失败 → RefundFailed → retryAfterSalesRefund）
```

## 7. 验收要点（e2e）
1. **Completed 入口**：订单进入 Completed 后可发起售后；未完成（AddingItems/PaymentSettled 未发货）不可发起。
2. **售后期**：超窗口拒绝创建。
3. **退款到账**：processAfterSalesRefund 后，Vendure `Refund` 达到 `Settled`、`AfterSalesRequest.state=Refunded`、`actualRefundAmount ≈ refundAmount`、`refundTransactionId` 非空。
4. **库存回补**：confirmReturnReceived 实收数量回补到原发货仓，restockJson 留痕。
5. **失败重试**：模拟退款失败 → RefundFailed → retryAfterSalesRefund → Refunded。
6. **越权**：他人订单售后单不可被查询/操作（customer.user.id 校验）。
