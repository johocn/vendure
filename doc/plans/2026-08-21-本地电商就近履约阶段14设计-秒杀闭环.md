# 阶段14 · 秒杀闭环（Flash Sale Closure）设计

> 日期：2026-08-21
> 项目：Vendure 本地化电商（d:\zhao\vendure）
> 前置：阶段13（拼团闭环）已完成
> 本文档为设计稿，实施见 companion 文件：`2026-08-21-本地电商就近履约阶段14实施计划-秒杀闭环.md`

## 1. 背景与目标

阶段13 已打通**拼团闭环**，价格促销工具箱拥有：优惠券 + 拼团。**秒杀**（限时限量的爆款引流玩法）在 `packages/flash-sale-plugin` 只有**半成品骨架**，业务闭环断裂：

- 无抢购入口：没有 shop mutation 把秒杀活动绑定到当前订单（拼团有 `joinGroupBuy`）
- `flashSalePriceAction` 用 **硬编码 `args.flashPrice`**，且 `flashSaleDiscountCondition` 不校验活动存在/状态/窗口 → 秒杀价无法按活动动态生效
- 库存/限购不闭环：`checkEligibility`（含 `reserveStockAtomic`）是**孤儿方法无人调用**，且与 `OrderPlaced.incrementSoldCount` **库存双计**
- 订单取消回滚 `releaseStock(ctx, activityId, 1)` **固定 1 件**，秒杀多件时会回滚数量错误
- e2e 仅 3 个空查询用例，无任何业务流验证

本阶段目标是**打通秒杀闭环**，复用阶段13验证过的模式（runtime 连接注入 + condition state 传 action + 原子占库存），让「建活动 → upcoming/active/ended 状态机 → 抢购（限购+库存原子占用）→ 秒杀价生效 → 支付 → 售罄/结束/取消回滚」形成可验证的完整链路。

## 2. 范围

### 2.1 目标（In Scope）
1. **秒杀价自动生效**：订单绑定 `flashSaleActivityId` → Promotion 按活动 `flashPrice` 动态折算（复用原生结算机制，不改订单状态机）
2. **抢购一体**：`applyFlashSale(activityId)` 校验活动（active/窗口）→ 校验限购（`limitPerUser`）→ **原子占用库存**（防超卖）→ 写订单 customFields（activityId + startAt/endAt 快照）→ 重算价格
3. **库存闭环**：占用即扣 `soldCount`（未支付也占用，防高并发超卖）；订单取消按**实际秒杀件数**回滚；`soldCount >= totalStock` → 售罄置 `ended`
4. **限购**：同一客户对同一秒杀活动的进行中/完成订单数 < `limitPerUser`
5. **状态机**：`upcoming → active → ended`（定时任务 + 售罄即时置 ended）
6. **e2e 全链路**：建活动/状态机/抢购价/限购拦截/售罄/取消回滚/动态取价

### 2.2 非目标（Out of Scope）
- 秒杀 + 优惠券 / 拼团 的叠加规则
- 定时上下架秒杀商品（仅状态机流转，不含库存商品的启用/禁用联动）
- 多规格秒杀（每活动仅一个 `variantId`，与现有实体一致）
- 秒杀库存与商品物理库存的合并扣减（RedisStockPlugin 未装时走 DB fallback，物理库存交给原生 StockLevel）

## 3. 领域模型（沿用现有实体，仅补逻辑）

```
FlashSaleActivity (秒杀活动)
┌────────────────────────────────┐
│ name / startAt / endAt          │
│ flashPrice   秒杀价(分)          │
│ totalStock   活动总库存           │
│ soldCount    已占用/已售          │
│ limitPerUser 每人限购             │
│ productId / variantId           │
│ status: upcoming | active | ended│
└────────────────────────────────┘
```

Order 自定义字段（沿用现有，`applyFlashSale` 时写入）：
| 字段 | 类型 | 说明 |
|------|------|------|
| `flashSaleActivityId` | int | 绑定的秒杀活动 ID（结算 Promotion 据此动态取价） |
| `flashSaleStartAt` | datetime | 活动开始时间快照（展示/校验兜底） |
| `flashSaleEndAt` | datetime | 活动结束时间快照 |

## 4. 核心机制

### 4.1 抢购闭环（applyFlashSale 一体）
```
shop: applyFlashSale(activityId)
  → 校验活动存在 + status='active' + startAt ≤ now ≤ endAt
  → 限购校验：同客户该活动进行中/完成订单数 < limitPerUser（超限抛错）
  → 原子占用库存（防超卖）：
       Redis 路径   : reserveStock(`flash-sale:<id>`, qty)，余量 < 0 → 售罄
       DB fallback : UPDATE ... SET soldCount = soldCount + qty WHERE ... AND soldCount + qty <= totalStock
       受影响=0 → 售罄抛错
  → 写 order.customFields { flashSaleActivityId, flashSaleStartAt, flashSaleEndAt }
  → orderService.applyPriceAdjustments 重算 → 秒杀价立即生效
```

**库存占用时机决策**：抢购成功即占用（非支付时），因为秒杀高并发下「下单即占」是防止超卖的标准做法。`soldCount` 语义 = 已占用（含未支付）。未支付订单最终取消会回滚，不造成永久占用。

### 4.2 结算闭环（复用原生 Promotion）
```
价格套用：
  flash_sale_discount condition: order.customFields.flashSaleActivityId 非空
    → 运行时查 FlashSaleActivity → 校验 active/窗口/soldCount<totalStock（imo期满即不优惠）
    → 返回 state { variantId, flashPrice }
  flash_sale_price action: 命中秒杀变体行 → 折扣 = unitPrice - flashPrice（>0 才折让）
```

条件/动作复用阶段12/13 `runtime` 模式：`onApplicationBootstrap` 注入 `TransactionalConnection` 到模块级变量，Promotion condition/action 静态构造但延迟取连接异步查活动配置。

**Promotion 配置**：管理端创建**一张**促销「秒杀价」= `flash_sale_discount` 条件 + `flash_sale_price` 动作，两者**无参数**（活动配置运行时动态读取），因此无需随活动创建/编辑/删除维护促销。原 `flash_sale_eligibility` 独立资格条件的窗口/限购校验并入 mutation 层与 discount condition，删除以保持单一职责（避免订单每次重算额外查库）。

### 4.3 库存/售罄 / 结束
- **售罄**：占用库存后 `soldCount >= totalStock` → 活动置 `ended`（即时）
- **结束**：定时任务每分钟把 `status='active' && endAt <= now` 置 `ended`；已 `ended` 活动 `applyFlashSale` 拒绝
- **取消回滚**：`Order` 进 `Cancelled` 时，按订单内匹配 `variantId` 的秒杀行**总件数**回滚 `soldCount`（修正现有固定 1 件）；`soldCount` 递减用 `WHERE soldCount - qty >= 0` 防负

### 4.4 限购
- 在 `applyFlashSale` mutation 层做（一次性入口），非 Promotion：`findByCustomerId` 该客户订单过滤 `customFields.flashSaleActivityId === 活动` 且 `state !== 'Cancelled'`，数量 ≥ `limitPerUser` → 抛 `Purchase limit exceeded`
- 避免在订单每次价格重算时查限购（性能），故不放入 Promotion condition

## 5. 状态机

```
FlashSaleActivity.status：
 upcoming ──(startAt ≤ now)──► active ──(endAt ≤ now)──► ended
   │                              │
   │(定时任务)                     │(soldCount >= totalStock 即时)
   └──────────────────────────────┴────────────────────► ended
```

## 6. API 变更

### Shop
- `applyFlashSale(activityId: ID!): Order` —— **新增**：抢购一体 mutation，校验 → 占库存 → 写订单字段 → 重算价格。返回更新后订单（前后端可直接读 `activeOrder`）
- `activeFlashSaleActivities: [FlashSaleActivity!]!`（已存在，不动）

### Admin
- `createFlashSaleActivity / update / delete / list / detail`（已存在，不动）；`update` 维持 `soldCount/status` 白名单防篡改

## 7. e2e 场景

1. **建活动 + 初始态**：建 `upcoming`（startAt 在未来）→ 状态 upcoming；`activeFlashSaleActivities` 为空
2. **抢购全链路**：建 active 活动（flashPrice < 原价）→ 加购秒杀变体 → `applyFlashSale` → 订单价 = 秒杀价（掉落 = 原价 - flashPrice）→ 支付成功
3. **动态取价**：两张不同 flashPrice 的活动，同变体不同活动抢购 → 各自生效对应秒杀价（验证非硬编码）
4. **限购拦截**：`limitPerUser=1` → 第一单成功，第二单 `Purchase limit exceeded`
5. **售罄**：`totalStock=2` → 两单后 `soldCount=2`，活动 `ended`，第三单 `Sold out`
6. **取消回滚**：抢购占用+取消 → `soldCount` 回落，可重新抢购
7. **库存双计修复验证**：占库存后 `soldCount` 精确 = 占用件数（不因 OrderPlaced 再累加）
8. **校验拦截**：活动未开始/已结束/非 active 抢购被拒

## 8. 风险与注意
- **库存占用时机为抢购时**：未支付也占用 `soldCount`，语义 = 已占用；订单取消回滚，文档明确此模型
- **仅占不扣物理库存**：RedisStockPlugin 未装时 DB fallback 满足秒杀内部防超卖；商品物理库存交原生 StockLevel
- **Promotion 动态取价的并发**：占用是原子 UPDATE，结算期查到 `soldCount < totalStock` 才优惠；临界并发秒杀价可能超卖 0.1% 级，可接受（秒杀本身有限量）
- **重复 applyFlashSale 幂等**：同一活动重复绑定同一订单仅提示/幂等处理，不重复占用库存
