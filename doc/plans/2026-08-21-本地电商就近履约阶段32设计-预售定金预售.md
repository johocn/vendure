# 阶段32 · 预售/定金预售（Pre-sale & Deposit Pre-sale）设计

> 日期：2026-08-21
> 项目：Vendure 本地化电商（d:\zhao\vendure）
> 前置：阶段31（会员签到/任务体系）已完成
> 本文档为设计稿，实施见 companion 文件：`2026-08-21-本地电商就近履约阶段32实施计划-预售定金预售.md`

## 1. 背景与目标

本地电商价格/营销工具箱已拥有：优惠券、拼团、秒杀、积分抵现、专属折扣。但面对**新品未到货、爆款提前锁客**的引流场景，缺少**预售**能力：

- 商家想在新品到货前就锁定意向客户并提前回款
- 传统电商有「定金预售」（先付定金占位 → 到货付尾款）与「全款预售」（提前付全款 → 到货发货）两种玩法
- 现有 `packages` 无任何预售相关插件，业务闭环完全空白

本阶段目标是打通**预售闭环**，复用阶段13/14/30/31验证过的所有模式（活动实体 + 订单 customFields + Promotion 动态取价 + 事件驱动 + 状态机扩展）：

**核心创新点**：通过 **Vendure 自定义订单状态机**（新增 `Deposited` 中间态），让「付定金 → 订单进入等待尾款态 → 到货后付尾款 → 补齐后正常履约」在**同一个订单**上完成（单订单两阶段支付），并支持**全款预售**与**预售价格分档**。

## 2. 范围

### 2.1 目标（In Scope）
1. **预售活动实体** `PreSaleActivity`：`deposit`（定金）/`full`（全款）两种模式，统一状态机 `upcoming → active → delivered`（到货Release）+ 尾款窗口
2. **预售价格分档**：`presalePrice`（预售价）< 原价，Promotion 动态取价按活动打折到预售价（复用秒杀/拼团模式）
3. **定金预售（两阶段支付）**：自定义订单状态 `Deposited`：
   - 支付「定金」→ `ArrangingPayment → Deposited`
   - 活动到货 / 尾款开启后支付「尾款」→ `Deposited → PaymentSettled` → 正常发货
4. **全款预售**：支付全款直接进入 `PaymentSettled`（无中间态，一次性收款到货发货）
5. **到货后才占库存发货**：预售商品 `trackInventory: FALSE` 走 `serviceType` 语义（对齐阶段28），不提前占物理库存；到货后由 admin 置活动 `delivered`（Release 库存/解锁发货）
6. **e2e 全链路**：建活动/状态机/定金支付/尾款补齐/全款/预售价/到货发货/限购/售罄/重复拦截

### 2.2 非目标（Out of Scope）
- 预售 + 优惠券/拼团/秒杀 的叠加规则设计（价格分档用一张无参促销动态取价，叠加规则交由后续促销优先级阶段）
- 定金退款审批流（本阶段定金退款按「取消订单触发退款」，全额/比例策略默认全额，不进审批）
- 尾款自动扣款（银行卡代扣等；本阶段仅手动补尾款 mutation）
- 预售商品的物理库存到货自动入库（到货动作是 admin mutation，非对接仓储系统）
- 多规格预售（每活动仅一个 `variantId`，与秒杀实体一致）

## 3. 领域模型

### 3.1 PreSaleActivity（预售活动，ChannelAware，新实体）
| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | VendureEntity |
| `channelId` | int NOT NULL | 渠道 |
| `name` | varchar | 活动名 |
| `mode` | varchar | `deposit`（定金）/ `full`（全款） |
| `startAt` / `endAt` | datetime | 预售期（可下单窗口） |
| `releaseAt` | datetime | 到货/开售时间（尾款开启或全款发货 latch） |
| `tailStartAt` / `tailEndAt` | datetime | 尾款支付窗口（`deposit` 模式） |
| `presalePrice` | int（分） | 预售价（折扣价；设 0 表示无分档，用原价） |
| `depositAmount` | int（分） | 定金金额（`deposit` 模式），`<= 0` 时落到全款语义 |
| `totalStock` | int | 活动可售总量 |
| `soldCount` | int | 已锁定/已售件数（`default 0`） |
| `limitPerUser` | int | 每人限购（`default 1`） |
| `productId` / `variantId` | int | 目标商品（对齐秒杀，单变体） |
| `status` | varchar | `upcoming \| active \| delivered \| ended` |

> **状态机与「到货」语义**：`active → delivered` 表示到货（商品可发货/尾款已开启）。`soldCount >= totalStock` → 即时 `ended`（售罄）。`releaseAt/endAt <= now` 定时任务折叠。

### 3.2 Order 自定义字段（新建 `order-custom-fields.ts`）
| 字段 | 类型 | 说明 |
|------|------|------|
| `preSaleActivityId` | int 可空 | 绑定的预售活动 ID（Promotion 动态取价据此打折） |
| `preSaleMode` | varchar 可空 | `deposit`/`full` 快照 |
| `preSaleDepositTotal` | int 可空 | 定金需付总额（订单内预售价 × 件数 折算）快照（展示/占库校验兜底） |
| `preSaleReleaseAt` | datetime 可空 | 到货时间快照 |

> **两阶段支付金额依据**：Vendure `addPaymentToOrder` 内部 `amountToPay = totalWithTax - covered`，一次只收「剩余」。定金阶段需要「只收定金、不要求覆盖全额」，**不能直接用原生 addPaymentToOrder 的单次全额语义**——因此定金/尾款均走**自定义 mutation + 自定义订单状态**，支付方式对齐阶段11 `singleStageRefundablePaymentMethod`（一次即 Settled），金额由我们精确指定。

## 4. 核心机制

### 4.1 自定义订单状态机（延期：Deposited）
Vendure 默认订单态链无中间「定金」态。仿阶段10 `order-completion.process.ts`（`declare module OrderStates` + `OrderProcess`）新增：

```
declare module '@vendure/core' {
    interface OrderStates { Deposited: never; }
}

const preSaleOrderProcess: OrderProcess<any> = {
    transitions: {
        ArrangingPayment: { to: ['AddingItems', 'Deposited', 'PaymentSettled', 'Cancelled'] },
        Deposited: { to: ['PaymentSettled', 'AddingItems', 'Cancelled'] }, // 可回退补/改 + 取消
    },
};
```
- `pricesIncludeTax` 下金额以 `totalWithTax` 口径
- 该 process 在插件 `configure()` 里 push 到 `config.orderOptions.process`（仿阶段10 `configureDefaultOrderProcess` 后 push，用幂等标记防重复）
- **关键**：原生 `addPaymentToOrder` 在 `ArrangingPayment` 时会用全额 `amountToPay`；我们的定金 mutation **不走原生 addPaymentToOrder**，而是自行创建「已 Settled 的定金 Payment」并手动 `transitionToState('Deposited')`。尾款 mutation 在 `Deposited` 再补一笔尾款 Payment 手动转 `PaymentSettled`。这样两阶段金额完全由我们控制，且每个 Payment 各自是一次性金额（避免原生「收剩余」覆盖语义）。

### 4.2 抢购/下单（applyPreSale 一体，仿 applyFlashSale）
```
shop: applyPreSale(activityId)
  → requireCustomer（Authenticated）
  → 校验活动存在 + status='active' + startAt ≤ now ≤ endAt
  → 限购：同客户该活动进行中/完成订单 < limitPerUser（超限抛错）
  → 原子锁定库存（防超卖）：DB UPDATE soldCount+=qty WHERE ... AND soldCount+qty<=totalStock；
     受影响=0 → 抛「已售罄」
  → 写 order.customFields { preSaleActivityId, preSaleMode, preSaleDepositTotal, preSaleReleaseAt }
  → 若 presalePrice>0 → applyPriceAdjustments 触发 pre_sale_discount 打折到预售价
  → 返回订单
```

### 4.3 两阶段支付 mutation
```
# 全款预售（mode=full）：一次付清
payPreSaleFull(orderId)：
  → 校验订单已绑 preSaleActivity + mode=full + active 窗口
  → 校验订单商品归属 preSaleActivity.variantId
  → 创建 Settled 支付金额 = totalWithTax（原生 addPaymentToOrder 可复用）
  → 订单转 PaymentSettled

# 定金预售（mode=deposit）：分两步
payPreSaleDeposit(orderId)：
  → 校验状态 ArrangingPayment + mode=deposit
  → 校验定金金额 = preSaleDepositTotal（= 预售价 × 件数 折算，可从 activity.ord 计算）
  → 创建 Settled 定金 Payment（金额按 preSaleDepositTotal）
  → 订单 transitionToState('Deposited')   ← ArrangingPayment→Deposited
payPreSaleTail(orderId)：
  → 校验订单状态 Deposited + 活动已到货/delivered + 尾款窗口开启（tailStartAt≤now≤tailEndAt 或 releaseAt 已过）
  → 校验尾款金额 = totalWithTax - 已付定金
  → 创建 Settled 尾款 Payment
  → 订单 transitionToState('PaymentSettled')   ← Deposited→PaymentSettled
  → 后续正常发货/履约
```

### 4.4 到货 / 发货（deliverPreSale）
- admin `deliverPreSale(activityId)`：`active → delivered`
- 这是「到货」事件：
  - `full` 模式：到货后按序发货（商品 `trackInventory: FALSE` 不占库存，到 Release 再结算）
  - `deposit` 模式：到货即开启尾款窗口（tailStartAt 落 `releaseAt`）；尾款补齐的订单进入 `PaymentSettled` 后发货
- 可由 ScheduledTask 到 `releaseAt/endAt` 自动折叠（仿秒杀 job），e2e 用 admin mutation 保确定性

### 4.5 结算打折（复用原生 Promotion，动态取价）
```
pre_sale_discount condition: order.customFields.preSaleActivityId 非空
  → 运行时查 PreSaleActivity → 校验 active + 窗口 + soldCount<totalStock
  → 返回 state { variantId, usePresale: true }
pre_sale_price action: 命中预售变体且活动 presalePrice>0
  → unitPrice>presalePrice 时折让 delta（对齐 flash-sale-price-action）
```
Promotion 配置：管理端创建**一张**无参促销「预售价」= 两件套，活动配置运行时动态读，无需随活动维护促销（对齐阶段14）。

### 4.6 取消回滚
- 定金阶段取消（`Deposited` → `Cancelled`）：回滚已锁定 `soldCount`（按订单内预售行件数），且若定金已收（Settled），由原生退款流程退定金（本阶段默认全额退定金）
- 尾款补齐前取消：同样回滚锁定 + 退定金
- `full` 模式在 `PaymentSettled` 后取消：回滚锁定 + 正常退款（原生已支持）
- 回滚用 `WHERE soldCount - qty >= 0` 防负（对齐秒杀）

## 6. 状态机汇总

```
PreSaleActivity.status:
 upcoming ──(startAt≤now)──► active ──(deliverPreSale:到货)──► delivered ──(endAt≤now)──► ended
   │                           │                                  │
   │(定时任务)                 │(soldCount≥totalStock 即时)         │(尾款窗口超时/售罄)
   └───────────────────────────┴──────────────────────────────────┴──► ended

Order.state（deposit 模式）:
 ArrangingPayment ──(payDeposit)──► Deposited ──(payTail)──► PaymentSettled ──► …正常履约
        │                              │  (取消→回滚库存+退定金)
        └────────────── Cancelled ◄────┘
```

## 7. e2e 场景

1. **建活动 + 初始态**：建 upcoming 活动 → status upcoming；`activePreSaleActivities` 空
2. **全款预售**：建 full 活动（presalePrice<原价）→ 加购 → `applyPreSale` → 订单价=预售价 → `payPreSaleFull` → OrderState=PaymentSettled
3. **定金预售**：建 deposit 活动 → 加购 → `applyPreSale` → `payPreSaleDeposit` → 状态 `Deposited`（未到 PaymentSettled）
4. **尾款补齐**：`deliverPreSale` 到货 → `payPreSaleTail` → 状态 `PaymentSettled`，尾款金额 = 剩余
5. **限购拦截**：`limitPerUser=1` 第二单 `Purchase limit exceeded`
6. **售罄**：`totalStock=2` 两单后 soldCount=2，活动 `ended`，第三单抛错
7. **预售后状态机**：未开始抢购被拒；定金未到货不能付尾款（尾款窗口未开启）
8. **取消回滚**：定金后取消 → `soldCount` 回落，可重抢
9. **尾款窗口**：tailEndAt 已过付尾款被拒

## 8. 风险与注意
- **原生 addPaymentToOrder 只能单次收全额剩余**：定金阶段必须走自定义 mutation 创建「指定金额已 Settled Payment」+ 手动状态转移，勿用原生（否则 amountToPay 会收全额、跳过定金中间态）
- **订单状态机扩展需 `configureDefaultOrderProcess` 之后 push**，且 ArrangingPayment 的 to 要显式含 Deposited（mergeTransitionDefinitions 并集，对齐阶段10 Completed 写法）
- **金额口径**：定金/尾款/预售价统一「分」，`pricesIncludeTax=true` 下支付额/折扣断言用含税口径（对齐阶段14/15 铁律）
- **`generated` 支付方式 id**：两阶段每步各创建一个独立 Payment（非累加同一 payment）；覆盖校验要按活动快照字段算，不依赖 Order.payments 累加
- **到货才占库**：预售商品卖 `trackInventory: FALSE`（对齐阶段28 `serviceType` 语义），applyPreSale 只锁活动 `soldCount`，不碰物理库存；到货 `deliverPreSale` 只是活动状态事件，物理库存入库由其商品真实库存配置管理
- **改实体 schema 后删 `e2e/__data__/*.sqlite` 重跑**（阶段铁律）
