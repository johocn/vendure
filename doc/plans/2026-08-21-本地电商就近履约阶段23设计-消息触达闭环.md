# 阶段23 · 设计（消息触达闭环：站内信 + 微信接口化）

依据：本地电商已具备订单（Vendure core）、退款/售后（after-sales-plugin）、拼团（group-buy-plugin）、秒杀（flash-sale-plugin）、店铺（shop-plugin）、消息中心（strapi zhao-sso：模板/任务/AB/微信通道）。

核心：新建 `@vendure/notification-plugin`，用 Vendure `EventBus` 订阅领域事件驱动消息触达。通知对象覆盖**买/卖双方**；落地双通道——**站内信真实落地**（InboxMessage 实体，本地可验收）+ **微信接口化**（调用 strapi zhao-sso 微信模板任务，本地不真实验证，接口即契约）。

## 1. 目标与非目标

**目标**
- 事件驱动：订单/退款/开店营业/拼团/秒杀等状态迁移事件自动产生通知。
- 站内信真实：买/卖双方各自的消息收件箱，可查询、可已读、本地 e2e 可验收。
- 微信接口化：通过 strapi zhao-sso 的 `msg-jobs`/`buildJob` 投递微信模板，复用模板/AB/幂等能力。
- 场景覆盖（先行四类）：订单状态变更、退款/售后闭环、店主营业提醒、拼团/秒杀结果。

**非目标**
- 不做短信/邮件/企微等多通道（保留扩展点，见通道抽象）。
- 不改 `wechat-subscribe-message-plugin`（既有微信模板逻辑，避免破坏）。
- 不自行在 notification-plugin 内重新实现模板/去重/AB——全部复用 strapi zhao-sso。
- 微信侧不在本地做真实端到端（无真实模板），只保证「接口契约 + 可配置 URL + 失败留痕」。

## 2. 总体架构

```
Vendure 应用
  EventBus 订阅（领域事件驱动，幂等）
   ├─ OrderStateTransitionEvent     付款 Settled / 发货 Shipped / 送达 Delivered / 完成 Completed
   ├─ RefundStateTransitionEvent    退款 Settled（到账）
   ├─ 拼团 group-buy 事件            成团 / 过期取消
   ├─ 秒杀 flash-sale 事件           中签 / 售罄
   └─ 店主营业事件                    新订单（店主侧）
        │
   NotificationService 编排：scene → 模板 → 收件人(买家/店主) 解析
        │
        ├──►【站内信·真实】InboxMessage 实体落库
        │     recipientId: Customer.id | Administrator.id
        │     ├─ shop-api  C端 myInbox 只读 + markInboxRead
        │     └─ admin-api 店主/平台 inbox 只读 + markRead
        │
        └──►【微信·接口化】HTTP → strapi zhao-sso /msg-jobs
             复用微信模板通道；接口化、URL 可配置；失败写日志不阻断主流程
```

## 3. 数据模型

在 `packages/notification-plugin/src/inbox-message.entity.ts`：

- `id`、`createdAt`、`updatedAt`（core 基类）。
- `channelId`：`int` 普通列 NOT NULL（对齐阶段17/19 ChannelAware 铁律）。
- `recipientType`：`enum('customer','admin')`（varchar 列，避免跨库枚举）。
- `customerId`：`int nullable`；`administratorId`：`int nullable`。二者按 recipientType 二选一。
- `scene`：`varchar`，业务场景编码。
- `title`、`content`：`varchar`/`text`。
- `link`：`varchar nullable`。
- `isRead`：`bool` 默认 false。
- `readAt`：`Date nullable`（可选 Date 列，勿写死 type，阶段11 铁律）。

无 ChannelAware `channels` 关联（manage ManyToMany）——通知与渠道正交，服务内一律 `{ channelId: ctx.channelId }` 过滤。

## 4. 事件编排器（NotificationService）

- `onApplicationBootstrap` 订阅各 EventBus 事件类型，回调进 `handle(event)`。
- 统一管线 `dispatch(req)`：
  1. `scene` 归一与收件人解析（买家 = order.customer / 店主 = order 涉及 shop 的 administratorId）。
  2. 站内信：`createInbox` 写入 InboxMessage（真实落库）。
  3. 微信：调用 strapi `NotifierProvider`（见 §5），把 scene 映射到 strapi 模板 code 调 `buildJob`；失败 catch 只 Logger.warn，不阻断站内信已成功。
- **事件 order 关系不完整**（阶段4/5/15 铁律）：StateTransitionEvent 的 order 不一定加载 customer/customFields，须用 `orderService.findOne(id, [relations])` 重载后再读归属。

### 4.1 订单状态变更
- `ArrangingPayment→PaymentSettled`（付款成功）→ 买家「订单支付成功」。
- `→Shipped` → 买家「已发货」。
- `→Delivered` → 买家「已送达」。
- `→Completed` → 买家「交易完成」。

### 4.2 退款 / 售后闭环
- `RefundStateTransitionEvent → Settled` → 买家「退款到账」，金额用 `refund.total`（含税，见阶段11）。

### 4.3 店主营业提醒
- 新订单（付款成功）→ 涉及店铺的店主 `administratorId` 各一条「新订单通知」。
- 通过 `getOrderShopIds`（address-plugin 的聚合：line→productVariant.productId→Product.shopId）解析店主。跨插件依赖走 lib 直取，避免 DI 环。

### 4.4 拼团 / 秒杀结果
- 复用既有插件事件类型（group-buy-plugin / flash-sale-plugin 暴露的 EventBus 事件）；成团/中签 → 参团/抢购用户通知；过期取消/售罄 → 相关用户通知。

## 5. 微信接口化（NotifierProvider 抽象）

- `WechatNotifierProvider` 实现 `NotifierProvider`，通过 HTTP 调 strapi：
  `POST {STRAPI_BASE}/api/zhao-sso/v1/admin/msg-jobs/anonymous`，body = `{ userId, scene, templateCode, params, link }`（对齐 accept-msg-center.cjs 契约，走 anonymous 端点，Bearer token 可配置）。
- `NotificationPluginOptions`：`strapiBaseUrl`、`strapiAdminToken`、`templateSceneMap`（scene→strapi templateCode）、`enabled`（开关）、`adminApiRoot` 等均可配置，**禁止硬编码**（用户偏好）。
- 微信侧失败：只 catch + `Logger.warn` + 可选的发送日志表留痕，绝不影响站内信成功路径。

## 6. GraphQL 接口

**shop-api（C 端，`@Allow(Permission.Authenticated)` + requireCustomer）**
- `myInbox(options): InboxMessageList!`：当前登录顾客的收件箱（按 createdAt DESC，limit 分页，返回未读数）。
- `markInboxRead(input): InboxMessage!`：置已读（仅本人；他人 Forbidden）。
- `inboxUnreadCount: Int!`：未读数。

**admin-api（店主/平台）**
- `orderInbox(options): InboxMessageList!`：当前 login 管理员（Administrator）的收件箱。
- `markInboxRead(input): InboxMessage!` 同款。
- 店主域加 `@Allow(manageOwnShop.Permission)` 场景可复用 shop-plugin 数组权（可选，先行给平台 UpdateSettings + Authenticated）。

## 7. 错误处理

- 微信通道不配 URL/token → 跳过微信，仅站内信，Logger.warn 一次。
- strapi 返回错误 → catch，站内信不受影响。
- 无店主（商品未归属店铺）→ 跳过店主通知。
- 事件 order 无 customer → 跳过买家通知（不抛）。
- 站内信落库失败 → Logger.error，不影响主流程。

## 8. 测试（e2e，≥12）

复用 address-plugin e2e 骨架（plugins 数组含 ShopPlugin.init({}) 用于店主解析）。覆盖：
1. 插件加载 + 空 inbox 返回空
2. 付款成功触发买家站内信（event→inbox 断言）
3. 发货/送达/完成各触发一条
4. 退款 Settled 触发「退款到账」
5. 店主通知：新订单写对应 administratorId 的 inbox
6. C 端 myInbox 隔离（A 看不到 B）
7. markInboxRead 置已读 + 仅本人
8. inboxUnreadCount 递增/清零
9. 未登录 shop-api 401
10. 订单无顾客 / 无店主 跳过（防御）
11. 微信 notifier 未配置 → 仅站内信、主流程不抛
12. 微信 notifier 配置 URL → 发出 HTTP（mock 断言调契约）

## 9. 风险与前置依赖

- 依赖 `Product.shopId`（shop-plugin）+ 店主 `Shop.administratorId`（阶段18）进行店主解析；e2e 用 createShop + assign 准备。
- 依赖 strapi zhao-sso 的 msg-jobs API 契约；未起 strapi 时微信通道置 disabled 即可通过 e2e。
- 拼团/秒杀事件类型需要从对应插件导出（若尚未导出则先行补充 export，不改其内部逻辑）。
- Order custom 字段/关系依赖 core；事件关系不完整按「findOne 重载」规避。
