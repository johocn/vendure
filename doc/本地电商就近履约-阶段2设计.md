# 本地电商 · 就近履约（阶段2）设计说明

> 目标：在阶段1「就近分配 + 超区门禁」基础上，补全**剩余闭环**：多库库存展示、订单供销存中间表（进销存/售后关联）、售后退货库存回补、库存分配机制明确、移库进入账本、自提点履约落地。
> 依赖：阶段1已具备 `NearestStockLocationStrategy`、`inventory-plugin`（入库/出库/调拨/盘点单）、`delivery-plugin`、`after-sales-plugin`、cjk `PickupLocation`。

---

## 一、现状盘点（阶段1交付的能力）

| 能力 | 位置 | 状态 |
|---|---|---|
| 就近分配 + 服务城市门禁 | `logistics-plugin/nearest-stock-location-strategy.ts` | 已上线（订单按 lat/lng 就近 + 按 city 过滤服务仓） |
| 基础库存模型 | core `StockLocation / StockLevel / StockMovement`（ALLOCATION/SALE/RELEASE/ADJUSTMENT） | 已用 |
| 入库/出库/调拨/盘点单 | `inventory-plugin`（`RKT/CKT/DBT/PDT`） | 已实现状态机 | 
| 配送履约 | `delivery-plugin`（assigned→in_progress→delivered，推动 Fulfillment Shipped→Delivered） | 已实现 |
| 超时取消 | `order-timeout-plugin`（`shouldAllocateStock() = toState!=='Cancelled'` 已修复库存泄漏） | 已上线 |
| 售后（退款） | `after-sales-plugin`（Pending→Approved→Returning→Received→Refunded） | 已上线 |
| 自提点 | cjk `PickupLocation` + `pickupLocations(lat,lng)` + store/pickup-point/employee handler | 已有，未接入就近闭环 |

**关键缺口（阶段2要补的）：**

1. **多库库存展示**：前端仅用 `stockLevel` 聚合值（单一口径），无"每个门店/仓库各有多少货"的逐仓明细。
2. **无供销存中间表**：core 的 `StockMovement` 与 `inventory-plugin` 的入库/出库/调拨/盘点单相互独立，订单行从哪个仓出货、何时扣、售后是否退回，分散在多个表，无法一站式追溯。
3. **售后退货不回补库存**：`after-sales.service.processRefund` 只退款，退货入库后库存不增加。
4. **移库在途未入账本**：`StockMoveOrder` 状态机齐全，但其流水不与其他进出库统一。
5. **自提未形成闭环**：`deliveryType=pickup` 可写，但发货/核销/自提点库存联动未打通。

## 二、多库库存展示（前端逐仓明细）

### 2.1 现状
- 前端 `ProductVariantFragment` 只有 `stockLevel`（core `stockLevelForSell` 汇总值），商品详情页 `ProductDetails.vue` 用 `stockLevelMap` 显示"有货/缺货"，无法体现"哪个门店有几件、离你多远"。

### 2.2 方案
新建 Shop API 查询（`logistics-plugin` 或新 `nearstore-plugin`），一次返回某商品的逐仓可售库存 + 距离：

```graphql
extend type Query {
  variantNearbyStock(
    productId: ID!
    # variantId 为空时返回该商品全部 variant 的各仓库存
    variantId: ID
    lat: Float
    lng: Float
  ): [NearbyStockItem!]!
}

type NearbyStockItem {
  productId: ID!
  productName: String!
  productSlug: String!
  # 各门店/仓库
  location: StockLocationBrief!
  stockOnHand: Int!
  stockAllocated: Int!
  stockAvailable: Int!   # stockOnHand - stockAllocated
  distanceKm: Float!      # haversine（无定位时为 -1）
}

type StockLocationBrief {
  id: ID!
  name: String!
  lat: Float
  lng: Float
  serviceCities: [String!]
  description: String
}
```

- **后端**：复用 `inventory-plugin.findStockLevels + findStockLocations` 与 `logistics-plugin/location-utils.distanceKm`，按 lat/lng 距离升序 + 按服务城市过滤返回。
- **前端**：
  - 商品详情页新增「附近门店库存」区块：由 `variantNearbyStock` 渲染门店卡片，显示 `有货 X 件 · 距你 Y 公里`，支持一键选最近自提点。
  - 保留商品级聚合 `stockLevel` 作为"可购买总数/售罄兜底"。
- **口径统一**：`stockAvailable` 向后端 `assertSufficientStock` 的可售口径保持一致（`onHand - allocated`），避免前端显示可买、后端下单却说缺货。

## 三、供销存中间表（订单 ↔ 进销存 ↔ 售后 统一账本）

**一句话**：以"行级库存流水账本"作为订单、进销存单据、售后三者之间的唯一关联中间表，任何库存增减都写一条，任何一端都能按单号追出完整链路。

### 3.1 新增实体 `OrderStockLedger`（`inventory-plugin/entities/order-stock-ledger.entity.ts`）

| 列 | 类型 | 说明 |
|---|---|---|
| id | ID | |
| code | string | 账本单号 `YSZ+时间戳` |
| productVariantId | ID | 关联 SKU |
| variantSku / variantLabel | string | 冗余快照，便于追溯 |
| stockLocationId | ID | 发生仓/门店 |
| bizType | enum | `order` / `afterSales` / `stockIn` / `stockOut` / `stockMove` / `stocktake` / `manual` |
| bizCode | string | 业务单号（orderCode / afterSalesCode / RKT.. / DBT.. 等） |
| orderLineId | ID nullable | 关联订单行（bizType=order/afterSales 时） |
| direction | enum | `in`（入库/回补）/ `out`（扣减/发货） |
| quantity | int | 正数，方向由 direction 表达 |
| beforeOnHand / afterOnHand | int | 变动前后 onHand 快照（对账用） |
| balanceLocationId | ID nullable | 移库/跨仓时另一端（如调拨目标仓） |
| reason | string | 业务说明（如 `order#xxx:fulfill-sell`、`afterSales#xxx:return-restock`） |
| createdAt / updatedAt | timestamp | |

### 3.2 写入时机（钩子/服务）
- **下单占货**（ALLOCATION）：可写 `direction=out` 但**不扣 onHand**（占 allocated），或仅用于留痕。建议 ledger 只记录 **real onHand 变动**，占货走 core ALLOCATION/`stockAllocated`，避免账本与 core 双记重复对不上。
- **发货扣货**（Fulfillment Shipped → SALE）：`direction=out`，扣 onHand，`bizType=order, bizCode=orderCode`。**这是 main 的 keyOut**。
- **售后退货入库（Received → 回补）**：`direction=in`，加 onHand，`bizType=afterSales, bizCode=afterSalesCode, orderLineId, reason=return-restock`。**这是 keyIn（回补）**（见第四节）。
- **入库单入库**：`direction=in, bizType=stockIn`。
- **出库单出库**：`direction=out, bizType=stockOut`。
- **调拨发/收**：源仓 `out` + 目标仓 `in`（balanceLocationId 互指），`bizType=stockMove`。
- **盘点差异**：`direction=in/out, bizType=stocktake, reason=reconcile`。
- **手工调账**：`bizType=manual`。

> 复用 `inventory.service.adjustStockForLocation` 的统一入口，在写 `StockAdjustment` 流水的**同一事务**内写 ledger，保证一致性。

### 3.3 追溯查询
- 按 `orderCode` → 查该订单所有行各自的 `进(退货/调拨入) / 出(发货/售后出) / 在途` 流水 → 即"供销存台账"。
- 按 `afterSalesCode` → 查退货对应的回补记录。
- 提供后台列表接口（Admin `ledgerList`）。

## 四、售后退货库存回补（关键补点）

**现状缺陷**：售后 `Returning→Received`（收到退货）后只把状态转到 `Received`，退款走 `processRefund`，但**该仓 `stockOnHand` 未增加**。

**方案**：在 after-sales `confirmReceive`（Returning→Received）增加库存回补：

```ts
async confirmReceive(ctx, id): Promise<AfterSalesRequest> {
  return this.connection.withTransaction(ctx, async txCtx => {
    const request = await repo.findOne(...其中 orderLine 明细 + 原分配仓);
    // 状态校验 Returning→Received
    // 1. 定位源头：该售后行对应订单行，找其原发货仓
    //    （订单行快照 customFields /* allocation location */ 或查该行已写的 ledger bizType=order 的 locationId）
    const locationId = await this.resolveSourceLocation(txCtx, request);
    // 2. 回补库存：+request.recoverQty（默认=orderLine 数量）
    await inventoryService.adjustStockForLocation(txCtx, orderLine.productVariantId, locationId,
      +recoverQty, `afterSales#${request.code}:return-restock`);
    // 3. 写 ledger：bizType=afterSales, direction=in, orderLineId, bizCode
    // 4. 状态 -> Received（沿用现有流转，退款仍走 processRefund）
  });
}
```

- **回补数量**：`recoverQty = min(orderLine 数量, 本次实收数量)`；售后单需要记录「实收数量」字段（新增 `receivedQuantity`），部分退货按实收回补。
- **回补仓库**：优先回**原发货仓**（写 ledger 时记录的 `stockLocationId`），保证就近仓与顾客取得关联的仓库存回到位；若查不到则回补到售后指定的收货仓（后台可选）。
- **已取消订单的售后**：`orderLineId` 对应行可能从未发货，此时不分配库存回补（回补量为 0 或跳过），避免对不上。

## 五、库存分配机制明确

**口径（延续阶段1 + 已修复的历史 bug）**：

1. **下单即锁定**：`addItemToOrder` 后 `NearestStockLocationStrategy.forAllocation` 按订单 `lat/lng` 就近 + 按 `city` 过滤服务仓，交给 `MultiChannelStockLocationStrategy` 做库存核算，写 `ALLOCATION`（占 `stockAllocated`，`availableStock = onHand - allocated` 扣减）。前端下单前据此展示可买性。
2. **发货转销**：Fulfillment `Shipped` 时 core 写 `RELEASE`(释放 allocated) + `SALE`(扣 onHand) 两条，`order-stock-ledger` 记 `out` 主链路。
3. **超时/取消**：`order-timeout-plugin` + `shouldAllocateStock()=toState!=='Cancelled'` → 取消只 `RELEASE` 回滚 allocated，不扣 onHand（已在阶段1修复泄漏）。ledger 不记（real onHand 未变）。
4. **售罄兜底**：`stockAvailable<=0` 时前端禁购 + 后端 `assertSufficientStock` 抛错，双保险。
5. **库存策略矩阵**：阶段2**不引入按渠道/等级的策略矩阵**（归阶段3），仅保留现有"就近优先 + 渠道隔离(MultiChannel)"。如需"同一订单多仓拆单出库"，另做（当前单仓履约）。

## 六、移库机制明确（进入账本）

`inventory-plugin` 已有完整移库状态机，阶段2仅做**账本化 + 在途不参与可售**：

- **Pending**：创建移库单，**不占用/不扣库存**。
- **InTransit（ship）**：源仓 `adjustStockForLocation(-qty)` + 写 ledger `bizType=stockMove, direction=out, balanceLocationId=target`，此时源仓 onHand 已减，启用 `在途库存`（新增 `inTransit` 字段或仅依赖账本推导），目标仓未到，`可售 = onHand - allocated - inTransit`。
- **Received（receive）**：目标仓 `+qty` + 写 ledger `direction=in, balanceLocationId=source`，在途清零。
- **Completed**：仅状态。
- **Cancelled**：
  - Pending 取消：无库存操作。
  - InTransit 取消：源仓 `+qty` 回滚 + ledger 记 `rollback-source`（现状已实现回滚，只需补 ledger）。
- **校验**：移库 `assertSufficientStock` 沿用；金额单价（`unitPrice`）保留在调拨单行，供进销存成本核算。

## 七、自提点履约闭环

**现状**：cjk `PickupLocation` + `pickupLocations(lat,lng)` + `store-pickup / pickup-point / employee-pickup` handler 均有；`order.deliveryType` 已可写。

**补全闭环**：

1. **结算页选择自提点**：前端调 `pickupLocations(lat,lng)`，选点后写订单自定义字段：
   `deliveryType='pickup'`、`selectedPickupLocationId` / `pickupLocationName/Address`（快照），结账时落库。
2. **自提点即就近分配锚点**：`NearestStockLocationStrategy` 在 `deliveryType=pickup` 且带 `selectedPickupLocationId` 时，用**自提点坐标**替代顾客定位参与就近排序（先补该自提点所在门店/仓，其次就近补货仓）。
3. **发货**：后台对 pickup 订单用 `store-pickup`（门店自提）或 `pickup-point`（自提点自提）handler 创建 Fulfillment → Shipped（写 SALE + ledger out），库存从分配仓扣。
4. **核销**：交付到点后标记 `pickupClaimed`（可在 delivery-plugin 增加 `confirmPickupHandover` 或复用 `markDelivered`），推动 Delivered。
5. **到店提示**：前端订单详情展示自提点名称/地址/门店营业时间。

## 九、验证

- 双仓建库存 → 前端 `variantNearbyStock` 按距离排序显示两仓分别有货。
- 下单发货 → ledger 出现 `order:out`；售后退货 `Received` → 原仓 `onHand` 增加 + ledger `afterSales:in`，金额核对一致。
